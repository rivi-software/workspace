# Architecture

Single Cloudflare Worker (`workers/app.ts`) that exports `fetch`, `email` and `scheduled` handlers (the last a cron, every minute: snoozes waking, scheduled send and mailbox imports, `workers/scheduled.ts`). The UI is TanStack Start (SSR, file-based routes under `app/routes`, loaders and mutations as server functions) built with the Cloudflare Vite plugin. The handlers are `createWorker` (`workers/worker.ts`) with Start's request handler (`@tanstack/react-start/server-entry`) passed in: `fetch` serves a file of an earlier build from the `PREVIOUS_ASSETS` namespace, Better Auth at `/api/auth/*` (`app/lib/auth.server.ts`) and the Workspace API at `/api/v1/*` (`app/lib/api/api.server.ts`) itself, everything else through Start, and puts the security headers on every answer (`nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY` and `frame-ancestors 'none'` unless the response set a frame rule of its own, HSTS over HTTPS); `email` hands inbound mail to `app/lib/mail/ingest.server.ts`; errors that escape `fetch` or `email` are reported to PostHog and rethrown. The tests run the same Worker with a stand-in for Start (`test/worker-entry.ts`), so they reach Better Auth and the API through `SELF.fetch` without the Vite build. Server code reaches bindings with `import { env } from "cloudflare:workers"`; the current Request comes from `getRequest()` inside server functions and server route handlers (`app/lib/request.server.ts`).

## Data model (D1)

Better Auth's tables are part of the Drizzle schema (`users`, `sessions`, `accounts`, `verifications`, `passkeys`, `two_factors`), so a change to any of them is a migration like any other. Better Auth keeps its dates as integer milliseconds (`instant` in the schema); the app's own columns are ISO text.

- `users`: a person and their mailbox: `email` is the primary address on `MAIL_DOMAIN` (sign-in, delivery, From), `role` admin or member, `active` (deactivated people keep their mail but cannot sign in), `last_sign_in_at`; Better Auth's `email_verified` (true from the start: a mailbox here is the workspace's own), `image`, `updated_at` and `two_factor_enabled` (whether a password sign-in asks for an authenticator's code); `preferences_json` (the mail preferences, `app/lib/mail/preferences.ts`); `vacation_*` (the responder, its subject and text, its first and last day). Better Auth never inserts a person: admins do (`createPerson`).
- `sessions`: a person signed in on one browser (Better Auth's `session`): `token` (what the session cookie, and a bearer token, carry), `expires_at` (14 days, moved on while it is used), `ip_address`, `user_agent`. Written by Better Auth alone; deleted by "Sign out everywhere", a new password and a deactivation (`revokeSessions`), and with the person.
- `accounts`: how a person signs in (Better Auth's `account`): one `credential` account per person holds their `password` (PBKDF2, as `hashPassword` writes it; the seed and `scripts/create-admin.mjs` write the same). The token columns are for a social provider, which this workspace has none of.
- `verifications`: a short-lived value Better Auth keeps between two steps (a passkey's challenge, a two-factor state).
- `passkeys`: a person's passkeys (Better Auth's passkey plugin): `name` (what they called it), `public_key`, `credential_id` (what a sign-in names, unique), `counter` (the authenticator's signature counter), `device_type` and `backed_up` (synced to a cloud account or not), `transports`, `aaguid`, `created_at`. Only the public key: no biometric or private key ever reaches the server. Deleted with the person, or by an admin (`removeAllPasskeys`).
- `two_factors`: a person's authenticator app (Better Auth's two-factor plugin): the TOTP `secret` and the `backup_codes`, both encrypted with the auth secret, `verified`, and the lockout after too many wrong codes (`failed_verification_count`, `locked_until`). Deleted with the person, or by an admin (`resetTwoFactor`).
- `signatures`: a person's signatures: `name`, `text` (the plain-text signature, or the text reading of `html`), `html` (null for a text signature; sanitised on save by `sanitizeSignatureHtml`, its images `data:` URIs of at most 256 KB each), `is_default` (what a new message starts on) and `is_reply_default` (what a reply or forward starts on), each true on at most one per person (a partial unique index each; one signature can be both).
- `aliases`: extra addresses delivered to a mailbox (`hello@`, a former name), which the owner can also send from.
- `recovery_addresses`: a person's personal addresses outside `MAIL_DOMAIN` (three at most) where a reset link may go, with `confirmed_at` once the person opened the link mailed to it.
- `recovery_tokens`: a single-use link mailed to a recovery address, as the SHA-256 of its token: `purpose` `confirm-address` (with `recovery_address_id`, deleted with the address) or `reset-password`, and `expires_at` (24 hours and 30 minutes). Deleted when used; rows that expired a day ago are pruned when a new one is made, and younger ones count towards five links of a kind per person an hour.
- `threads`: a conversation in one mailbox: `folder` is inbox, archive, spam or trash; `trashed_at` (when it went to the trash or spam: 30 days later `pruneExpired` deletes it for good); `snoozed_until` (out of the inbox until then; `wakeSnoozed`, from the cron each minute, brings it back); `muted`; `starred`; counters (`message_count`, `unread_count`, `sent_count`, `has_attachments`); `participants_json` (everyone but the owner), `snippet`, `last_message_at`. Starred, Snoozed, Sent, Drafts, All mail (everything but spam and trash) and a label are views: starred threads, snoozed ones, threads with `sent_count > 0`, the `drafts` table, the folders, `thread_labels`. A thread the owner starts sits in the archive (so under Sent) until the first reply brings it to the inbox.
- `messages`: one email: `direction`, the RFC 5322 `message_id` (unique per mailbox), `in_reply_to`, `references_header`, the addresses as JSON, `subject`, `text`, `html` (as received, sanitised when shown), `date`, `read`, `raw_key` (the `.eml` in R2, inbound only), `delivery_status`, `list_unsubscribe`, `spam_json` (why the spam filter put it in Spam when it arrived, with the rules and the reasons), `spam_learned` (`spam` or `ham`: what it taught the spam filter, so Report spam or Not spam on it later takes that back first).
- `labels`: a person's labels: `name` (unique per person) and `color` from the palette in `app/lib/mail/folders.ts`; `thread_labels` puts one on a thread (both cascade when the label or the thread goes).
- `contacts`: the people a person has written to or heard from (`email`, `name`, `times_used`, `last_used_at`), kept on every send and delivery (spam aside), for the composer's suggestions; never the owner's own addresses or a no-reply. `written_at` is when the person last wrote to them: the spam filter never sends such a sender's mail to Spam.
- `filters`: a person's rules, in `position` order: `conditions_json` (from, to, subject, words, has an attachment) and `actions_json` (skip the inbox, mark read, star, a label, trash, spam, never spam), `app/lib/mail/filters.ts`.
- `sender_rules`: a sender a person blocked (their mail goes to Spam) or allowed (it never does): `sender` is a lower-cased address or a domain behind its at (`@acme.com`, its subdomains too), `verdict` `block` or `allow`; an address's rule decides before its domain's, at most 500 per person.
- `image_senders`: a sender whose images from the web a person always loads, matched as `sender_rules` are; mail in Spam never loads them by itself.
- `spam_tokens`: what a person's spam filter learnt: per `token` (a word of the text, `subject:` a word of the subject, `from:` the address, `from@` its domain, `reply@` a Reply-To's domain, `url:` a linked site, `file:` an attachment's extension) the number of messages learnt as `spam` and as kept mail (`ham`) it came up in; the row `" messages"` counts the messages. Words counted nowhere, or once and not seen for 120 days, are pruned with the trash.
- `attachments`: a file of a message in R2 (`r2_key`), with `content_id` and `inline` for the images an HTML part embeds.
- `drafts`: a message being written: `mode` (new, reply, forward), the owner's message it answers (`in_reply_to_id`), the recipients as JSON, subject, `html` (the rich composer's markup) and `text`, the signature it goes out with (`signature_id`). `scheduled_at` makes it a scheduled message (under Scheduled, not Drafts; the cron sends it then), and `send_error` says why its scheduled send failed. `draft_files` holds the files chosen for it, in R2 under `draft/<user>/<file>`, until it is sent or discarded.
- `mail_imports`: a mailbox being copied in (Settings → Mail → Import): `provider` (`microsoft`), `account` (the source mailbox), `status` (`running`, `done`, `failed`, `cancelled`; one running per person), `tokens_sealed` (the Microsoft tokens, encrypted; null once it ends), `folders_json` (where each source folder's mail goes), `cursor_json` (how far the import is), the counters `total`, `imported`, `duplicates`, `left_out` with `left_out_json`, `attempts`, `last_error`, `lease_until` (a batch holds it until then) and `finished_at`.
- `drive_nodes`: a folder or file in Drive: `user_id` is the owner (whose storage it counts towards), `parent_id` the folder it sits in (null at the root), `path` the ids of its ancestors each followed by "/" (a subtree is `path GLOB prefix*`; a node's ancestors are the ids in its own path), `kind`, `name` (unique among its non-trashed siblings: a clash gets " (2)"), `content_type` and `size`, `r2_key` (`drive/<owner>/<node>` in the DRIVE bucket), `status` (`uploading` until the bytes are whole, then `ready`), `upload_id` (R2's multipart upload while a large file arrives), `created_by` (the owner, or an editor of a shared folder), `trashed_at` (only on the node trashed itself: what is under a trashed folder is in the trash with it and comes back with it).
- `drive_shares`: a node its owner shared: `subject` is a person's id (with `user_id` the same, so the share goes with the person) or `everyone`, `role` `viewer` or `editor`, `owner_id` for "Shared with me" to name. A share on a folder covers its subtree; the strongest role on the node or an ancestor is the person's.
- `drive_stars`: a person's star on a node of theirs or shared with them; deleted with the node.
- `drive_links`: a node shared outside the workspace: `kind` `link` (anyone holding it, after `password_hash` when set) or `invite` (`email`, confirmed with a one-time code: `code_hash`, `code_expires_at`, `code_attempts`, `confirmed_at`), `token_hash` (SHA-256 of the token, what a request is looked up by) and `token_sealed` (so its creator and the owner can copy it again), `allow_download`, `expires_at` (null: never; 30 days unless the creator chose), `created_by`, `revoked_by` and `revoked_at` (a revoked row stays, as the record), `views`, `downloads`, `last_viewed_at`. Always viewer only. Deleted with the node.
- `signing_requests`: a request for signatures on a PDF: `node_id` (the file it was made from, null once deleted), `name`, `created_by` (who asked), `signer_id` (who signs on the workspace's side), `auto_sign` (the asker's saved signature signs once the customer has), `customer_name`, `customer_email`, `message`, `status` (`sent`, `customer-signed`, `completed`, `declined`, `cancelled`; expired is `sent` past `expires_at`, 30 days), `page_count`, `fields_json` (the fields placed on its pages: kind, party, page, box in fractions of the page), `values_json` (what was filled in), `original_key` and `original_sha256` (the PDF copied at sending, `signing/<id>/original.pdf` in the DRIVE bucket), `token_hash` and `token_sealed`, the customer's one-time code, each signature as a PNG with when it was given, `signed_key` and `signed_sha256` (the signed copy, `signing/<id>/signed.pdf`), `signed_node_id` (its copy in Drive), `completed_at`, `ended_at`, `decline_reason`, `reminded_at`.
- `signing_events`: a request's history, only ever added to: `kind`, `user_id` (null for the customer), `actor`, `ip`, `user_agent`, `detail`, `created_at`; the signed copy's certificate page is made from it.
- `hand_signatures`: a person's own signature (`png`, base64), saved on the Signatures page or in the editor; it signs for the workspace's side and auto-signs.
- `assistant_conversations`: a person's conversation with the Assistant: `title` (the first question's opening words), `updated_at` (the sidebar's order).
- `assistant_messages`: one turn of it: `role` user or assistant, `parts_json` (the AI SDK's UI message parts: the text, and each tool call with its input and output), and on an answer `model` with `input_tokens` and `output_tokens`. Deleted with the conversation.
- `calendar_events`: an event on a person's calendar: `title`, `description`, `location`, `starts_at` and `ends_at` (instants, the end exclusive; an all-day event's the UTC midnights of its first day and the day after its last), `time_zone` (the zone it was made in, which a repeat keeps its wall-clock time in), `repeat` (`none`, `daily`, `weekly`, `monthly`, `yearly`) and `repeat_until`.
- `calendar_attendees`: a colleague invited to an event: `status` `needs-action`, `accepted` or `declined`; deleted with the event or the person.
- `tasks`: a person's to-do: `title`, `notes`, `status` `open` or `done` (`completed_at`), `priority`, `due_on` (a day, "YYYY-MM-DD", or null). One from or linked to a GitHub issue keeps `github_repo`, `github_number`, `github_url` and what it last looked like (`github_title`, `github_state`, `github_synced_at`); one task per issue per person.
- `github_connections`: a person's GitHub for their Tasks: `login` and `name` as GitHub named the token's account, `token_sealed`; deleted on disconnect and with the person.
- `workspace_settings`: a workspace-wide setting an admin changes: `key`, `value`, `updated_by`, `updated_at`. `drive.external-sharing` `off` turns sharing outside the workspace off; without a row it is on.

KV holds what needs no row: the sign-in throttles and Better Auth's rate limits, the throttles of the public pages, whom the vacation responder answered, and when each person's trash and Drive were last pruned. R2 holds the mail (`raw/<user>/…eml`, `att/<user>/…`, `draft/<user>/…`) in `workspace-mail` and Drive's files and signing's copies in `workspace-drive`. Deleting a conversation forever removes its rows and its objects.

## Flows

- **Inbound.** Email Routing calls `email()` once per envelope recipient. The handler buffers the raw message, parses it (with its `List-Unsubscribe` headers, and whether a machine or a list sent it), resolves the mailbox (the recipient's address with its `+tag` removed, matched to `users.email` or `aliases.address`; none: `setReject`, so the sender gets a bounce), skips a Message-ID the mailbox already holds, runs the owner's filters over it, and files it with `fileMessage` (`filing.server.ts`, the `arrival` policy): it finds the thread (a message named by In-Reply-To or References; else, within 14 days, a thread with the same subject and the sender among its participants; else a new one), asks the spam filter (`judgeMail`) once the thread is known, writes the raw `.eml` and each attachment to R2, inserts the message, puts the filters' labels and star on the thread, and brings an archived, trashed or snoozed thread back to the inbox unless it is muted or a filter keeps it out. A failed insert takes the raw copy and a thread made for it back out. The people on it join `contacts`, unless it is spam. Afterwards, for mail that is not spam, the vacation responder answers a person (not a machine or a list) once in four days, with `Auto-Submitted: auto-replied`.
- **Spam filter.** `judgeMail` decides, in order: a filter that marks it spam; the owner's sender rules, an address before its domain; a filter's "never spam"; someone the owner wrote to (`contacts.written_at`: kept); a conversation already in Spam; a conversation the owner took part in (kept). The two "kept, known" steps are skipped when the sender's domain failed DMARC. Everything else is scored (`spamRules` in `spam.ts`): Cloudflare's `X-CF-SpamH-Score`, DMARC failed (more when the From is on `MAIL_DOMAIN`: a forgery of the workspace's own domain), SPF failed without a valid DKIM signature, a sender's name showing another address, a Reply-To on another domain, a program or a macro document among the files, a link whose text is another site's address, a shouted subject, no Message-ID, no date. Only the receiving block counts: the headers above the first `Received` line another server than Cloudflare's wrote, and in it the topmost `Authentication-Results` of `mx.cloudflare.net`. Then the learnt words: once the filter learnt 10 messages of each kind, Robinson's chi-square combining over the 150 strongest words adds up to 5 points for mail that reads like the person's spam, or takes up to 4 off for mail that reads like their own. At 5 points the message goes to Spam, with the points, the rules and the reasons in `spam_json`. What the message teaches: a kept known sender's or an allowed sender's mail as kept mail, mail the rules alone give 8 points or more as spam; filters teach nothing. `email.inbound` logs the verdict, the points and the rules, never the text.
- **Outbound.** The console's send (`sendAction`), the API's (`POST /api/v1/mail/send`) and the cron's (`sendDueDrafts`) each hand what the composer holds to `sendComposed`: the From as an address, the recipients as typed, the draft's id and any files sent along. It refuses what is typed that is not an address ("Check these addresses: …"), runs the checks of `sendMail` before it reads anything from R2, sends the draft's files and then the others, and deletes the draft once the message is filed; a refusal or a failure leaves the draft as it was. `sendMail` (which code that writes a message in the person's name calls itself: `sendAsPerson`, an unsubscribe by mail) checks the From (the owner's address or alias, the message going out under the owner's name), a recipient and the signature, adds the signature the composer chose (after a `-- ` line, above the quoted original of a reply or forward; an HTML signature's images as inline attachments), builds the two parts (the rich composer's markup sanitised as mail that arrives is, the text part made from it; or plain text with the quote in Gmail's `gmail_quote`), sets In-Reply-To and References for a reply, sends through `sendMail` of `@rivi-software/workers-mail` (SES, or the `EMAIL` binding), and only then files the message (`fileMessage`, the `sent` policy) with the Message-ID the provider gave it, so the other side's reply threads back, un-snoozes the conversation it answers and notes the recipients in `contacts`. A message to one of the owner's own addresses is one message with the copy Email Routing brings back, whichever is filed first, in Inbox and Sent. A provider error is shown in the composer and nothing is stored; the draft stays.
- **Send later.** "Send later" in the composer saves the draft, checks it as a send would, and sets `scheduled_at` (at most a year ahead). A scheduled message is listed under Scheduled, not Drafts; "Cancel send" clears `scheduled_at` and opens it in the composer. The cron (`sendDueDrafts`) takes what is due, oldest first, claims each by moving its time on ten minutes where nobody else did, sends it and deletes the draft; a failure clears `scheduled_at` and keeps the reason in `send_error`.
- **Import from Microsoft 365.** "Connect Microsoft 365" goes to `/api/import/microsoft/start`, which seals the state, the PKCE verifier and the person's id into a ten-minute cookie (`sealed.ts`) and sends the browser to Microsoft's authorize endpoint. The callback checks the cookie is the same person's and the state matches, redeems the code, reads the account and its folders, plans each folder and inserts the running import with the tokens encrypted. Each minute the cron (`runImports`) leases every running import nobody holds and works through it for 40 seconds or 100 messages: Graph's `/me/messages`, oldest first, keyset-paged on `receivedDateTime`; a message whose Message-ID the mailbox holds counts as a duplicate without being fetched; the rest is fetched as MIME (at most 25 MB) and filed by `importMessage` (`fileMessage`, the `history` policy): threaded, the thread put in the inbox when the message was in Outlook's Inbox (else the archive), starred when flagged, labelled with its folder and categories, outbound when it came from Sent Items or one of the person's addresses, read as it was. Filters, the vacation responder and notifications never see imported mail. An expired access token is refreshed; Microsoft refusing the connection ends the import as failed and drops the tokens; a `Retry-After` holds the import that long; a message that fails three batches in a row is left out so the rest goes on.
- **Composer.** One component (`components/composer.tsx`) on its own page and under a conversation. Its addresses are chips with suggestions from `contacts`; its text is a contentEditable area with a toolbar (pasted markup reduced to the tags the editor writes), the quoted original folded until asked for; its files go to the draft the moment they are chosen; the draft saves itself two seconds after a change and as a beacon when the page is left. Send with the undo delay on saves the draft, shows a toast that holds the send, and leaves; the toast's time up, or the tab closed, sends it; Undo opens the draft again.
- **Learning.** "Report spam" teaches the filter that the mail others sent in those conversations, the newest 50 messages, is spam; taking a conversation out of Spam to the inbox or All mail that it is not; the trash teaches nothing (`learnThreads`). A message learnt the other way before is taken back first (`spam_learned`). Blocking a sender from a message's menu adds the rule and moves the conversation to Spam. Undo takes back what its action taught (`restoreLearnt`).
- **Organising.** `applyThreadAction` does one intent on the owner's threads among the ids given (star, archive, trash, spam, inbox, read, unread, delete for good from the trash or spam, mute, unmute, snooze, unsnooze, label, unlabel) and answers its undo, a sealed record of what it changed, which the toast's Undo posts to `undoAction`: `undoThreadAction` puts exactly that back, checking nothing again. The cron wakes the snoozed threads whose time came in every mailbox each minute (`wakeSnoozed`), and opening a list wakes the reader's at once; every six hours per person (KV) a list also prunes the trash and spam folder after the response (`pruneExpired`).
- **Reading.** The `/mail` route is a layout: it loads the list (a view or a label, a search, a page) and renders its child beside it (split, on a wide screen) or in its place. Opening a thread marks it read. The HTML part goes through `sanitizeHtml` in the loader (scripts, frames, forms, handlers and dangerous URLs removed; `cid:` images rewritten to signed file links) and is shown in a sandboxed iframe whose document carries a CSP: no script, no form, images only from this origin until "Load images", or from the start when the sender is on the reader's `image_senders` and the conversation is not in Spam. The quote under a reply folds behind "Show quoted text", a `<details>` that needs no script. In the dark theme a message's colours are adapted (`colors.ts`), with its own dark-mode CSS over them. A reply or forward quotes the sanitised HTML in the composer, outside any frame, so the rich editor passes what it starts from through DOMPurify first.
- **Files.** `/api/files/$id?exp=&sig=` serves a message's file for six hours from an HMAC link, inline for images and PDFs, as a download otherwise; `/api/messages/$id/raw` (session) serves the original `.eml`.
- **People.** Admins create mailboxes under Settings → People (`createPerson`): an address on `MAIL_DOMAIN`, a generated one-time password shown once, written as the person's `credential` account. There too: aliases, roles, a new one-time password (`resetPassword`, which ends the person's sessions), "Sign out everywhere" for a person, their passkeys removed and their authenticator reset, and deactivation (the mail stays, the sign-in stops, the open sessions end).
- **Sign-in.** `/login` is a classic form POST handled by `passwordSignIn` (`sign-in.server.ts`): a post from another origin is refused first (`sameOriginPost`; Start's CSRF middleware covers server functions only), then the throttle (KV, 10 failures per client and address in 15 minutes), then a deactivated person is told so, then Better Auth's `signInEmail` checks the password against the `credential` account's hash, under its own rate limit (`kvRateLimit`, 20 a quarter hour on that path). A failure is counted; a success answers with Better Auth's cookies: the session cookie `workspace.session_token`, or, for a person with an authenticator app, the two-factor cookie and a redirect to `/two-factor?next=…`, whose form (`secondFactorSignIn`) posts the code to `verifyTOTP`, or a backup code to `verifyBackupCode`, with `trustDevice` for "Don't ask again on this browser for 30 days". A passkey signs in from the login page's button through the browser client (`authClient.signIn.passkey()`, `/api/auth/passkey/*`), then the page loads whole on the new session. `next` goes through `safeNext`: a path on this host, never another site. A session is a row in `sessions`, 14 days, read on every request (`getSessionUser` → `auth.api.getSession`, then the user row while `active`; `requireUser` redirects a stranger to `/login?next=`); Better Auth's `session.create` hooks refuse a deactivated person and stamp `last_sign_in_at`. `/logout` ends the session through Better Auth. "Sign out everywhere" is `revokeSessions`, which deletes the person's rows; a new password from an admin or a reset goes through `setPassword`, which writes the hash and revokes; the person's own change in Settings goes through Better Auth's `changePassword` with `revokeOtherSessions`, so the browser it was changed in stays signed in. Sign-up, Better Auth's own password reset, email verification, change-email and delete-user are off (`disabledPaths`). The `bearer` plugin lets the API take the session token as `Authorization: Bearer` (docs/API.md).
- **Forgotten password.** Under Settings → Account a person adds a recovery address with their current password (a recovery address can reset it, so an open session is not enough); it must be outside `MAIL_DOMAIN`, and it is mailed a link to `/confirm-recovery#<token>` from `no-reply@` on the mail domain (24 hours). `/forgot-password` takes the person's address and answers the same whatever it is; after the response an active person with confirmed addresses is mailed `/reset-password#<token>` at each (30 minutes), unless five went out in the past hour. The token is in the fragment, which no request carries, because Workers Logs keep every request's URL: the page reads it on the client (`useLinkToken`), drops it from the address bar and posts it to a server function. The reset checks the new password before it spends the link (deleting the row is what makes it single use), then voids the person's other reset links, ends every session (`setPassword`) and lifts the sign-in throttle for that client; the person keeps their passkeys, and an authenticator app still confirms the next password sign-in.
- **Drive.** Every Drive call takes the person acting and goes through the gate (`access.server.ts`): a caller finds candidates and `reachAll` keeps those the node exists for, the person has a role on (the owner's own, else the strongest share on it or an ancestor, with `everyone` counting) and that are whole (a file still uploading is its uploader's alone), under the caller's trash policy: `outside` (no ancestor trashed and not trashed itself), `own-trash` (that, or a node the person owns and trashed) or `trash-view` (the person's trashed nodes no trashed folder hides). A listing hands it a folder's non-trashed children; the views (`listView`) are the same rows found another way; a search is `LIKE` over names in their own drive and under every root shared with them (20 roots a query). An upload (`/api/drive/upload`, `upload.server.ts`) makes the file's row first with `status` uploading, so the key is settled: a file up to 32 MiB is one PUT whose body streams into the bucket; a larger one is a multipart upload started with `intent: "start"`, fed 16 MiB parts by PUT and completed with `intent: "finish"`. An upload that never finished is abandoned a day later and a trashed node deleted for good after 30 days (`pruneDrive`, after a Drive page's response at most once in six hours per person). Moving a node rewrites its subtree's paths in one statement; trashing marks the node alone; restoring puts it back, or at the root when its folder is in the trash itself. A file is served by `/api/drive/files/$id` to a session that may reach it, inline where a browser shows it, with Range requests for media, under its own sandbox CSP, and `frame-ancestors 'self'` for a PDF so the file page can frame it.
- **Signing a PDF.** Anyone who reaches a PDF of up to 15 MB opens the editor from its file page (`/drive/sign/new/$nodeId`), places fields on its pages (pdf.js, loaded in the browser only) for the customer or for the workspace's side, fills in that side's texts and boxes, names the customer and who signs, and sends (`createSigningRequest`): it needs sharing outside the workspace on, reads the PDF with pdf-lib (a protected one is refused), copies it to `signing/<id>/original.pdf`, and mails the request from the person's own mailbox, so it is in their Sent. The customer opens `/s/sign/$token`, mails themselves a code (five an hour, five tries, ten minutes), and with the pass it gives (a sealed cookie, 24 hours, `Path=/s/`) sees the PDF with their fields; they sign with one drawn or typed signature and consent (`customerSigns`, a conditional update from `sent`), or decline with a reason. The workspace's side signs next: with `auto_sign`, the asker's saved signature at once; else the signer is mailed and signs on `/drive/sign/r/$requestId`. `finish` claims that signature in one conditional update, makes the signed copy (the original's own form painted into its pages and taken out, the values and signatures drawn over it, a certificate page with the request, the original's SHA-256, each signer's time, address and browser, and the history), keeps it at `signing/<id>/signed.pdf` and completes the request; when any of that fails the claim is taken back. Only then does it file the copy in Drive beside the original for the asker and mail it to the customer. Every step is a row in `signing_events`.
- **Drive outside the workspace.** Anyone who reaches a node makes a link or an invite to it, viewer only; its creator or the node's owner revokes it. Every request from outside goes through the gate: `openLink` finds the token by its SHA-256 and opens it only while it is not revoked or expired, sharing outside is on (`workspace_settings`), and its creator is active and still reaches the node under `outside`; only then does it ask for the password, or an invite's confirmation, unless the request carries a pass for it. The page `/s/$token` shows a file's preview or a folder's contents with no session, no workspace navigation and no owner address; it links with plain anchors and posts its forms to itself (the password, mailing an invite's code, confirming it), which answer with a pass cookie (sealed, 24 hours or the link's end, `Path=/s/`). Its file route `/s/$token/file/$nodeId` serves through `fileResponse`, as the session route does, with `no-cache`, no referrer and `noindex`. Tokens that open nothing are counted per client in KV (30 in 15 minutes), wrong passwords per client and link (10), an invite's code has five tries and ten minutes. A page opened counts a view and a download a download.
- **Assistant.** A question is `POST /api/assistant/chat` with its conversation (none for a new one) and the person's message; `answerChat` files the question, runs the model (`AI_PROVIDER`: Workers AI or Anthropic through AI Gateway, or the mock) over the conversation's last 40 messages with the tools (at most 8 steps), and answers the AI SDK's UI message stream, which the page renders as it comes. The tools read only what the person may reach (Mail's `findConversations` and `readConversation`, Drive's `listView` and `reachFile`) and write nothing but a draft (Mail's `writeDraft`). The answer is stored before the stream closes, so the page's move to the new conversation's page finds it; a conversation is deleted with its messages, by the person alone.
- **Calendar and Tasks.** Everything is placed in the reader's zone, so the grid and the grouped list render only once the client has hydrated. An event is stored as instants with the zone it was made in, and `occurrences` (`calendar.ts`) steps a repeat in that zone; a loader fetches a day's leeway each side of the view and the client places the items. A task is due on a day, never a moment. GitHub is read with the person's own token through `callLink` (`link.ts`), which never fails the page: the section says GitHub did not answer. Marking a linked task done closes the issue first and keeps the task open when GitHub refuses.
