# Workspace for iPhone and Android: agent instructions

Workspace for iPhone and Android is a workspace in an app of its own on a phone: a thin [Tauri 2](https://v2.tauri.app) shell around the system's web view that opens the workspace the person names (README, Your workspace's address). It bundles no copy of the workspace, so every Worker release reaches it at once; only the shell has releases of its own. On an iPhone it is WebKit (iOS 16.4 and later, the oldest WebKit the workspace's stylesheet runs on); on Android the Android System WebView (Android 7 and later). The Home Screen and the launcher name it **Workspace**. The repository-wide rules are in the root [AGENTS.md](../AGENTS.md); this is a pnpm workspace package of its own (`pnpm-workspace.yaml`).

- Stack: Tauri 2 (`tauri` 2.12.5 and the opener plugin pinned exactly in `src-tauri/Cargo.toml`, `objc2` for one message to the iPhone's web view), the CLI from npm (`@tauri-apps/cli`), Rust pinned in `src-tauri/rust-toolchain.toml` with the iPhone, iOS Simulator and Android targets. `src/` is the start page, plain HTML, CSS and JavaScript with no build step (`src/tauri.d.ts` types the one global it calls; `tsconfig.json` checks it). `scripts/icons.ts` writes the icons (TypeScript through `tsx`), tested in `tests/` with Vitest. `src-tauri/gen/apple/` is the Xcode project and `src-tauri/gen/android/` the Android Studio project, both committed: `tauri ios init` and `tauri android init` wrote them once, and what they carry is edited in place (below). Their build output is git-ignored.
- Shell (`src-tauri/src/`): `lib.rs` wires the opener plugin and the start page's commands and starts the app (`tauri::mobile_entry_point`; `main.rs` is the desktop window `tauri dev` opens). `endpoint.rs` is which workspace the app opens: the address the person named, kept as `workspace.json` in the app's configuration folder, else the build's `plugins.workspace.url`, else none. `window.rs` opens the one web view on the start page (`src/index.html`), which asks for an address when there is none, goes on to the workspace, and says so when it cannot reach it. `workspace.rs` parses an address (`Workspace::parse` for the build's and the kept one; `Workspace::from_input` for what a person types: `https://` added, the origin alone kept, plain HTTP only in a debug build) and decides every navigation and new window: the workspace's origin and the start page stay in the app, `mailto:`, `tel:`, `sms:` and `facetime:` go to the system, and everything else in a frame stays as it would in a browser tab (Duo's prompt, Microsoft's sign-in, Stripe). A page's request for a new window on the workspace's own origin loads in the one web view instead; every other site opens in the phone's browser. A plain link to another site reaches the browser through a click script `window.rs` runs on each workspace page once it has loaded (`OUTWARD_LINKS`, by `eval` from `on_page_load`, since an initialization script is fixed before the person may have named the workspace), which asks for a new window instead: the web view reports a frame's navigations as it does the page's, so `on_navigation` has to let other sites stay. Every decision reads the workspace anew (`Endpoint::current`), since the person can name another while the app runs.
- The start page (`src/start.js`) calls three commands, `workspace_address`, `parse_workspace_address` and `set_workspace_address` (`endpoint.rs`), through `window.__TAURI_INTERNALS__`. They are permissions of the app's own manifest (`build.rs`, `tauri_build::AppManifest`) that only `src-tauri/capabilities/start-page.json` grants, to the app's local pages alone: no remote origin is named, so no workspace page, nor anything it frames or links, can call them. Nothing in the start page's address sets the workspace, only what the person types into its form, and the page checks the typed address before it keeps it: `/api/health` must answer `ok` (`checkWorkspace`; the route answers `Access-Control-Allow-Origin: *` for this, `app/routes/api/health.ts`), or a typo that named another site would leave the app there with no way back. A workspace's sign-in page links the start page with `?change` (`mobileAppStartPage` in `app/lib/mobile-app.ts`, shown only in the app), and the page shown when the workspace cannot be reached has **Use another workspace** too. `tauri.conf.json`'s CSP lets the start page reach the IPC and `https:` (the check), nothing else.
- iPhone: `window.rs` asks the web view for what WebKit gives Safari and not a WKWebView (`webkit`): the edge swipe back and forward, which wry turns on for the Mac alone, so a page opened in place has a way back, the page under the status bar, which WebKit would otherwise inset the page below and paint in the system's colour, and the app's name after the web view's own user agent, read through key-value coding (`userAgent`); a download lands in the app's Documents folder, which the Files app shows under On My iPhone › Workspace (`UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` in `gen/apple/workspace-mobile_iOS/Info.plist`), since WebKit would put it in a Downloads folder the sandbox does not have. The status bar follows the phone's appearance (`UIStatusBarStyle`), so it matches the workspace while its theme is "system". The launch screen is the workspace's canvas, light or dark with the phone (`Assets.xcassets/Canvas.colorset`).
- Android: `gen/android/app/src/main/java/software/rivi/workspace/MainActivity.kt` insets the web view by the system bars, a display cutout and the keyboard, as margins in a window whose background is the canvas colour of the phone's reading (`res/values/themes.xml`, `colors.xml`, `values-night/`), because the Android System WebView tells a page nothing about them and the page's `safe-area-inset-*` are 0 there; padding would not do, since a WebView draws its page over its padding. The back button goes back through the web view's history, which Tauri's `TauriActivity` does. wry gives the Android web view no download listener and no page of its own for a failed load, so `MainActivity.kt` adds both: `Downloads.kt` hands a download to the system's download manager, with the web view's cookies (the workspace's session) and user agent, into the phone's Downloads folder (the app's own before Android 10, which needs no storage permission), named from the `Content-Disposition` header by `ContentDisposition.kt`, since Android's own `URLUtil` reads its `filename*` only from Android 15. A file served `inline` is left alone: the web view hands the listener any file it cannot show without saying which frame it came from, and Drive's PDF preview is a frame on the file served inline, while every Download in the workspace asks for an `attachment` (`?download=1`). The Android System WebView has no PDF viewer either, so the workspace offers no PDF in place in the Android app: Drive shows its no-preview card with Download in place of the preview's frame. `Unreachable.kt` wraps wry's `WebViewClient` (set just after `onWebViewCreate`, so wrapped on the next turn of the main thread) and sends a failed load of the main frame back to the start page as `index.html?unreachable=<address>`, which says it cannot reach the workspace and tries that address again if it is the workspace's; the failed load and the history before it go, so the back button leaves the app from there. The Kotlin has JUnit tests in `gen/android/app/src/test/`, which `./gradlew :app:testUniversalDebugUnitTest` runs in `gen/android` once a build has written `tauri.build.gradle.kts`.
- The workspace tells the app apart by its user agent: the web view's own, which names the real system and browser version (Drive's signing evidence and Duo's and Microsoft's sign-in read it), with `RIVIWorkspaceApp/<version>` after it (`webkit::make_native` in `window.rs` on an iPhone, `MainActivity.kt` on Android, `with_app` for the desktop window; `app/lib/mobile-app.ts`): it counts passkeys as unsupported there (WebKit and the Android WebView answer a passkey request from a browser alone), leaves out the browser-notifications switch, offers **Use another workspace** on the sign-in page, and on Android offers a PDF to download rather than in place. The app bundles no copy of the workspace, so the agent token and the start page's addresses (`tauri://localhost/index.html`, `http://tauri.localhost/index.html`, `?change`) are a contract with every installed version: add to them, never rename them.
- Icons: `pnpm run icons` writes every icon of Workspace on a phone from `icon/icon.svg`, Workspace's own symbol on a 40 grid (four module tiles, the first lit in the signal green) as an ink tile edge to edge: the iPhone set into the Xcode project (`gen/apple/Assets.xcassets/AppIcon.appiconset/`), the Android launcher icon in its adaptive layers into the Android project (`gen/android/app/src/main/res/mipmap-*`, the glyph shrunk into the launcher's safe zone, `ANDROID_GLYPH_SCALE`), the PNGs the desktop window reads (`src-tauri/icons/`) and the workspace's Home Screen icons in `../public/` (`apple-touch-icon.png`, `icons/`); commit what it writes. Every iPhone icon is written without an alpha channel, which App Store Connect refuses. The tab's `public/favicon.svg` is the same drawing cut by hand on the 32 grid, its tiles on whole pixels at 16 px; change it with the SVG (`tests/icons.test.ts` reads both).

## Commands

From this directory:

- `pnpm run app:dev`: the app in a phone-sized window on this computer, against the local workspace (`http://localhost:5174`). Start the workspace first with `pnpm run dev` in the repository's root. It rebuilds when the shell changes; the start page and the workspace reload on their own.
- `pnpm run ios:dev`: the same in the iOS Simulator, or on an iPhone over USB. `pnpm run android:dev`: in an Android emulator (which reaches the computer as `10.0.2.2`, its IPv4 loopback: start the workspace with `pnpm exec vite dev --host 127.0.0.1`, since Vite listens on `::1` alone by default), or on a phone over USB; it needs `ANDROID_HOME`, `NDK_HOME` and `JAVA_HOME` (README).
- `pnpm run ios:build`, `pnpm run android:build`: a release build, which needs the signing the README names.
- `pnpm run icons`: the icons from `icon/icon.svg`; commit what it writes.
- `pnpm run check` (TypeScript over the scripts, the tests and the start page), `pnpm run lint` (Oxlint on the root config), `pnpm run test` (Vitest).
- `pnpm run rust:check`: `cargo fmt --check`, Clippy with warnings as errors, and the Rust tests. rustup installs the pinned toolchain and targets on the first run. On Linux the desktop build needs WebKitGTK (`libwebkit2gtk-4.1-dev`, Tauri's prerequisites). CI (`.github/workflows/mobile.yml`) runs `verify` and the Rust checks on Linux, Clippy for the iPhone target and a build for the iOS Simulator on a Mac, and builds the Android debug package, whose `.apk` is the run's `apk-test` artifact for three days, and runs the Kotlin's JUnit tests, when a pull request changes `mobile/`.
- `pnpm run verify`: all of the above but the builds.

## Gotchas

- A configured address (`plugins.workspace.url`) is built into the shell, and a changed one is a rebuild. It is configuration, not an environment variable, because the Tauri CLI carries only `TAURI_*` and `WRY_*` variables into Xcode's build of the Rust library. An address the person typed is kept apart from it and wins over it, also across development builds.
- `Workspace::parse` panics at launch on a configured address it refuses (plain HTTP to a public host): a broken build is better than opening the wrong site. A kept address it refuses counts as none, and the start page asks again.
- A new command for the start page is a name in `build.rs`'s app manifest, a `generate_handler!` entry in `lib.rs` and an `allow-<name>` permission in `capabilities/start-page.json`; tauri-build fails on a capability naming a permission that does not exist. Never add a capability with `remote`: a workspace page, a mail it shows, or a site it frames would get the command too. A command for the workspace itself is a design change: file an issue first.
- `tauri ios dev` and `tauri android dev` keep running while Xcode or Android Studio is open from `--open`: the IDE's build calls the Tauri CLI for the Rust part, which reads the running command's environment, so a Node.js version manager's `PATH` has to reach it.
- `gen/apple/project.yml` is what xcodegen made the Xcode project from, and `gen/apple/workspace-mobile_iOS/Info.plist` what the project builds with: a key goes into both, so a regenerated project (`tauri ios init` again) keeps it.
- The Android debug build allows cleartext HTTP (`usesCleartextTraffic` in `gen/android/app/build.gradle.kts`), which the emulator's `http://10.0.2.2:5174` needs, and declares `ACCESS_LOCAL_NETWORK` (`gen/android/app/src/debug/AndroidManifest.xml`), the runtime permission Android 16 and later keep a local network address behind: grant it on the emulator with `adb shell pm grant software.rivi.workspace android.permission.ACCESS_LOCAL_NETWORK`, or the app says it can't reach the workspace. A release build has neither, and `Workspace::from_input` takes HTTPS alone there. On an iPhone, `NSAllowsLocalNetworking` in the Info.plist lets a development build reach the computer's address over Wi-Fi.
- `build.rs` links the Android library with 16 KB page alignment, which Android 15 and later want on the phones that have such pages and Google Play requires of a new app; NDK 27 aligns to 4 KB by itself, and Android 16 then shows a compatibility dialog at launch.
- When the workspace cannot be reached, the iPhone keeps the start page, which says so and offers to try again; the Android System WebView would replace it with its own "Webpage not available" page, so `Unreachable.kt` loads the start page again with `?unreachable=`. The Kotlin names the start page `http://tauri.localhost/index.html`, as `is_start_page` in `workspace.rs` and `mobileAppStartPage` in `app/lib/mobile-app.ts` do: a change to where Tauri serves it changes all three.
- `src-tauri/gen/android/app/src/main/jniLibs/`, `tauri.properties`, `tauri.build.gradle.kts` and `tauri.settings.gradle` are written by every Android build and git-ignored by the project's own `.gitignore`; so are the Xcode project's `build/`, `Externals/` and `xcuserdata/`, and `src-tauri/gen/schemas/`, which tauri-build writes.
- The workspace's theme lives in its `localStorage`, which the shell cannot read, so the iPhone's status bar follows the phone's appearance, not a theme the person chose against it.
- Clippy runs `pedantic` with warnings as errors; `src-tauri/clippy.toml` lists names the docs use as words. `unsafe_code` is denied, and allowed in `webkit` alone (`window.rs`).
