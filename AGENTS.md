# Workspace: agent instructions

Workspace is an open-source workspace on Cloudflare Workers: **Mail** (every person has a mailbox on `MAIL_DOMAIN`, receives through Email Routing and sends through `@rivi-software/workers-mail`: Amazon SES once the Worker holds its key, the Email Service `send_email` binding until then and when SES refuses a message; OpenPGP signs, encrypts, opens and checks mail with keys the workspace keeps), **Drive** (folders and files in the `DRIVE` bucket, shared inside the workspace or outside it by a link or an invite under `/s/`, and PDFs sent for signatures under `/drive/sign` and `/s/sign/`), the **Assistant** (a chat over the person's own mail and files on Workers AI through AI Gateway, or Anthropic, or a mock; tools that search mail, read a conversation, search Drive, read a text file and prepare a draft), **Calendar** and **Tasks** (events with invited colleagues; to-dos linked with GitHub Issues through a personal token kept sealed). One Worker: TanStack Start on the Cloudflare Vite plugin, D1 with Drizzle, R2 for raw messages and files, KV for throttles and small state, sign-in on Better Auth (`app/lib/auth.server.ts`) with Duo as an optional second factor, single sign-on for other apps as an OpenID Connect provider (`app/lib/sso/`, [docs/SSO.md](docs/SSO.md)), and the Workspace API for other clients at `/api/v1` (`app/lib/api/`, [docs/API.md](docs/API.md)). The README covers the product and the deploy; [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) the layout, the data model and the flows; [GLOSSARY.md](GLOSSARY.md) the words. Write plain English in names, comments and docs; a comment says why.

## Commands

- `pnpm run dev`: `wrangler types`, then Vite on http://localhost:5174 with every binding in Miniflare. Inbound mail is a POST to `/cdn-cgi/local/email` (`pnpm run email:simulate "Subject" "Body"`), sent mail is written under `.wrangler/tmp/email/` instead of leaving the machine, and the cron runs only when asked: `curl "http://localhost:5174/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"`.
- First `cp .dev.vars.local.example .dev.vars` and `pnpm run setup` (the local D1 migrations plus the seed); sign in with `admin@example.com` / `password`. `.dev.vars.local.example` sets `AI_PROVIDER=mock`, so the Assistant answers without `wrangler login`; `workers-ai` or `anthropic` run the real model through the AI binding, which is remote even in local dev.
- `pnpm run check`: `wrangler types`, then `tsc -b` over `app/`, `workers/` and `test/`. `pnpm run lint` is `wrangler types`, then Oxlint on the Ultracite config (`oxlint.config.ts`) with the rules that read the types (oxlint-tsgolint over the tsconfigs: a promise nobody awaits or handles, a value stringified as `[object Object]`, a switch that misses a case), `pnpm run format:check` Oxfmt (`pnpm run format` fixes; Markdown and JSON are not formatted), `pnpm run contracts:check` requires `migrations/` to match `app/db/schema.ts` and every recorded migration to match its hash in `migrations/JOURNAL.json`. `pnpm run verify:static` is the four together.
- `pnpm run fix` is Ultracite's fix (Oxlint's autofixes, then Oxfmt), and three things run it for you: lefthook's pre-commit hook (`lefthook.yml`, put into `.git/hooks` by `pnpm install`) over the staged files, restaging what it changed and stopping the commit on what it cannot fix; Claude Code's PostToolUse hook (`.claude/settings.json`) over each file it writes, answering what is left; and VS Code with the Oxc extension on save (`.vscode/`). The hooks skip `wrangler types`, so a fresh clone runs `pnpm run check` once first.
- `pnpm run test`: Vitest inside workerd (`@cloudflare/vitest-plugin`) with the D1 migrations applied to a fresh database. `vitest.config.ts` pins the `vars` of `wrangler.jsonc` (so the tests see `example.com` whether `.dev.vars` exists or not), `AI_PROVIDER=mock`, an empty PostHog token and empty SES secrets; `recordingEmail()` in `test/fixtures.ts` stands in for the `EMAIL` binding.
- `pnpm run build` then `pnpm run build:check`: the production build, `wrangler deploy --dry-run` of it, and `workers-bundle-check` (`workers-bundle-check.config.ts`), which fails on a source map the assets would serve, a value shaped like a secret in the build, or a forbidden marker in the Worker. `pnpm run smoke` runs `scripts/smoke.mjs` against a running server (`BASE_URL`): sign-in, an inbound message, the inbox, the thread, a reply through the binding, Sent, search, a Drive upload with its listing, file route and search, a link outside the workspace, Better Auth's session and sign-out, the Assistant on the mock model, Calendar, Tasks, and the password reset pages. CI runs it against `wrangler dev --local` on the build.
- The push relay is `relay/`, a pnpm workspace package of its own (a stateless Worker in front of APNs and FCM that takes Web Push from a workspace; [relay/README.md](relay/README.md), [relay/AGENTS.md](relay/AGENTS.md)): `pnpm --filter rivi-workspace-push-relay run verify`, which CI runs. The workspace's side is off unless `PUSH_RELAY_URL` is set ([docs/PUSH.md](docs/PUSH.md)).
- The native iPhone app is `ios/` (SwiftUI, over the Workspace API: the sign-in asks for the workspace's address, checks it through `/api/health`, then signs in with the password and the authenticator's code as docs/API.md says), with its rules in [ios/AGENTS.md](ios/AGENTS.md) and its CI `.github/workflows/ios.yml`; `WorkspaceKit/` builds and tests on Linux too (`docker run --rm -v "$PWD/ios/WorkspaceKit:/pkg" -w /pkg swift:6.2 swift test`). A change to an API shape is a change to `ios/WorkspaceKit/Sources/WorkspaceKit/Models/` too.
- The phone app is `mobile/`, a pnpm workspace package of its own (a Tauri shell for iPhone and Android around the system's web view, opening the workspace the person names); its rules are [mobile/AGENTS.md](mobile/AGENTS.md), its CI `.github/workflows/mobile.yml`. The workspace tells it apart by `RIVIWorkspaceApp/` in the user agent (`app/lib/mobile-app.ts`), links its start page from the sign-in page (`mobileAppStartPage`), and lets any origin read `/api/health`, which the app checks an address with: all three are a contract with every installed app.
- `pnpm run verify` is the full gate. `pnpm run deploy` deploys the build (README, Deploy): the remote migrations, `deploy:assets`, then `wrangler deploy`, and `deploy:production` is the same. It is also the deploy command the Deploy to Cloudflare button gives Workers Builds, so whatever a deploy needs goes in it. CI is `.github/workflows/ci.yml`; deploys from `main` are `.github/workflows/deploy.yml`, behind the repository variable `DEPLOYMENTS_ENABLED`, with `scripts/deploy-checks.mjs` before (main only, no placeholder binding id) and after (`APP_URL` answers `/api/health`). `.github/workflows/update.yml` is a deployment's opt-in auto-update (`AUTO_UPDATE_ENABLED`, never in `rivi-software/workspace`): `scripts/upstream-update.mjs` merges the newest upstream commit whose CI passed, three-way from the last one the copy took (for a copy the button made, which shares no history, the upstream commit its files are closest to), so a copy's own `wrangler.jsonc` stays; keep the upstream CI workflow at `.github/workflows/ci.yml`, which it looks for. `.github/workflows/semgrep.yml` comments a pull request's new Semgrep findings, and `.github/workflows/rivi-bot.yml` runs RIVI Bot (rivi-software/tools) as `.github/rivi-bot.yml` on `main` says.

## Gotchas

### Configuration and the build

- `wrangler.jsonc` is the production configuration; `.dev.vars` overrides its `vars` locally. Never put a secret in `wrangler.jsonc` or commit `.dev.vars`.
- `worker-configuration.d.ts` is git-ignored and written by `wrangler types` (the `dev`, `check` and `build` scripts run it). It declares the secrets only when `.dev.vars` exists, so `app/env.d.ts` declares them for CI's typecheck; a new secret goes in `.dev.vars.example`, `.dev.vars.local.example` (its local value), `cloudflare.bindings` in `package.json` and there.
- `.dev.vars.example` is what the Deploy to Cloudflare button (README, Deploy) reads as the Worker's secrets: every name in it becomes a secret field on the button's page, prefilled with its value. So it holds the secrets alone, empty, never a var (a secret and a var of one name clash) and never a working value (it would go to production). Local development copies `.dev.vars.local.example`. `cloudflare.bindings` in `package.json` is the description the page shows beside each binding, var and secret. The scripts name the database by its binding (`DB`), since the button lets a deploy give it another name.
- `app/routeTree.gen.ts` is generated by `pnpm run dev`/`pnpm run build` and committed; Oxfmt and Oxlint ignore it.
- Start's import protection fails the build when a route component reads from a `*.server.ts` module: what the client renders lives in a plain module (`app/lib/mail/folders.ts`, `views.ts`, `reads.ts`, `drive/drive.ts`, `drive/signing.ts`, `assistant/assistant.ts`), and the server-only functions stay in `*.server.ts`, called from loaders and server functions. The components call server functions from the `actions.ts` modules (`app/lib/mail/actions.ts` and its siblings), which import the `*.server.ts` modules for their handlers only.
- A `*.server.ts` module the tests import must not import `app/lib/request.server.ts`: its `@tanstack/react-start/server` import only loads inside the Vite build, which is why `auth.server.ts` carries its own `isSecure`.
- The Worker is one module, `createWorker` in `workers/worker.ts`: `fetch` (earlier builds' assets, Better Auth, the API, then Start; the security headers on every answer, errors reported to PostHog), `email` and `scheduled`. `workers/app.ts` passes Start's handler and `test/worker-entry.ts` (the tests' `exports.default`, from `cloudflare:workers`) a stand-in that answers 404, since Start needs the Vite build. A new path the Worker serves itself goes into `route` there, and so into both; a test that needs Start to answer mounts `createWorker` with a Start of its own (`test/worker.test.ts`).
- pnpm 12 blocks a dependency's build script unless `pnpm-workspace.yaml` lists it under `allowBuilds`; a new dependency that compiles something (a native binary, a WASM blob) goes there, else it installs without building. `overrides` there pins transitive versions with advisories; remove one once its parent ships a fix.
- Nothing in the repository names a Cloudflare account: `wrangler.jsonc` carries placeholder ids until a deployment pastes its own (README, Deploy), and the tests and the smoke run against Miniflare alone.
- `scripts/create-admin.mjs` (`pnpm run admin:create --local|--remote --email … --name …`) makes or resets an admin straight in D1 through `wrangler d1 execute`: a new password hash, every session, every reset link and the authenticator app gone, the account active and admin. It is the way back in for a locked-out admin, and the way the first admin is made in production.
- `workers-bundle-check.config.ts` forbids markers, never modules: Rolldown writes no source map for the chunks of virtual modules (Start's manifest and server function resolver, its own runtime), and a module rule fails every file it cannot see into. A marker must also be in a file of the project outside `node_modules`, or the check calls it stale.
- The build writes `dist/server/wrangler.json` and points Wrangler at it through `.wrangler/deploy`, so `wrangler deploy` and `wrangler dev` after a build serve the build; `.dev.vars` is read beside that config (CI copies it to `dist/server/`).

### Database and migrations

- A schema change goes through Drizzle: edit `app/db/schema.ts`, run `pnpm run db:generate`, commit the new file under `migrations/` with its `meta/` snapshot. `contracts:check` fails on a schema that differs from the migrations, and drizzle-kit cannot ask about a rename in CI. `db:generate` also records the new file's SHA-256 in `migrations/JOURNAL.json` (`@rivi-software/d1-migrations`), and `contracts:check` fails once a recorded migration is edited or deleted: a migration that ran never changes, the next one does the work.
- drizzle-kit writes an added column's `REFERENCES` without its `ON DELETE` action (the snapshot keeps it), so read the SQL and add the action by hand.
- The deploy applies the migrations before the Worker (about 15 seconds apart), and Drizzle names every column of `schema.ts` in its selects, so dropping a column breaks the running Worker until the deploy lands. A drop that must not interrupt takes two releases: the schema without the column first, the drop after.
- Better Auth's tables (`users`, `sessions`, `accounts`, `verifications`, `passkeys`, `two_factors`) are in the same schema and migrate the same way. Its dates are integer milliseconds (`instant` in the schema); the app's own columns are ISO text.
- D1 binds 100 values a query, and the tests' Miniflare refuses the 101st too. A list of ids that can reach 100 (a page, a selection, "Mark all as read", a message's References) goes in as one JSON array through `json_each` (`inIds` in `mailbox.server.ts`, `trainTokens` in `spam.server.ts`) or in slices (Drive's `chunks` of 90, the shared roots 20 a query), never as `inArray` or a multi-row `values`.

### Sign-in (Better Auth)

- Better Auth is one instance per `Env` (`authFor` in `app/lib/auth.server.ts`, a `WeakMap`), so the tests' stand-in envs each get their own; `authFor` answers a promise, since Better Auth and its plugins are imported on first use (`loadBetterAuth`), not with the Worker: the module graph is large, and only a request that signs someone in or reads a session needs it. Its error class comes from the small `@better-auth/core/error`, never from `better-auth/api`, which pulls the whole graph in. `createAuth` reads `APP_URL` for `baseURL`, `trustedOrigins` and the passkeys' `rpID`: passkeys and the sign-in forms work at that origin alone.
- The Worker serves `/api/auth/*` before TanStack Start (`isAuthPath` in `workers/worker.ts`), as it serves `/api/v1/*`, so the tests reach both through `exports.default.fetch` (`cloudflare:workers`) without the Vite build.
- Sign-up, Better Auth's own password reset, email verification, change-email, change-password and delete-user are `disabledPaths`: admins make the accounts (`createPerson` in `users.server.ts`), a forgotten password goes through `recovery.server.ts`, and the person's own change through `changeOwnPassword`, whose `auth.api.changePassword` call `disabledPaths` does not close (it closes the HTTP routes) and which then ends the reset links (`revoke`). Better Auth's ids get the app's prefixes (`ID_PREFIXES`: `usr`, `ses`, `acc`, `ver`, `pk`, `tfa`).
- The password form is `passwordSignIn` in `app/lib/sign-in.server.ts`, one call from `/login`'s POST handler, in this order: `sameOriginPost` (Start's CSRF middleware in `app/start.ts` checks server functions only, not a route's own handlers; a form on another site would otherwise sign the browser in to the account it names), the form's own throttle (KV, 10 failures per client and address in 15 minutes: `loginThrottled`, `recordLoginFailure`, `clearLoginFailures`), a deactivated person told so, then `auth.api.signInEmail`. A post with neither `Sec-Fetch-Site` nor `Origin` passes, since no browser sent it; the smoke relies on that.
- Better Auth's own rate limits (`kvRateLimit`, a fixed window in KV, `customRules` per path) are a brake, not a lock: two requests in the same instant can both pass. The form's throttle is the one that counts failures.
- `/two-factor` (`secondFactorSignIn`) checks the origin the same way and posts the code, or a backup code, to Better Auth with the two-factor cookie the sign-in set; `trustDevice` is the 30-day checkbox. `next` always goes through `safeNext`: a path on this host, never another site.
- Sessions are rows in D1 (`sessions`), read on every request (`cookieCache` off), so ending one is immediate. A change of credentials goes through `revoke(db, userId, reason)` in `auth.server.ts`, and the reason alone decides what ends (`REVOCATIONS`): `sign-out-everywhere` the sessions; `new-password` (`setPassword`: an admin's one-time password, a reset link) and `deactivation` (`setPersonActive(false)`) the sessions and every reset link; `own-password-change` the reset links, after `changeOwnPassword` has gone through Better Auth's `changePassword` with `revokeOtherSessions` and answered the new session's cookie, so Settings keeps the browser signed in; `recovery-address-removed` the reset links, when `removeRecoveryAddress` took a confirmed one (a reset link names the person, not the address it went to). `removal` (`removePerson`) the sessions and every reset link, at once, before the cron deletes the rest of the person's rows. A new way to change a credential names its reason there, never deletes `sessions` or `recovery_tokens` rows itself; `endSession` signs one browser out and `listSessions` reads them for Settings. The `session.create.before` hook refuses a deactivated person on every way in.
- The password hash is the `credential` row of `accounts`, PBKDF2 as `hashPassword` writes it. `scripts/create-admin.mjs` and `scripts/build-seed.mjs` write the same format, so a hash they wrote signs in through Better Auth; keep the three in step.
- Passkeys and the authenticator app go through the browser client (`app/lib/auth-client.ts`, a plain module the pages import): `authClient.signIn.passkey()` on the login page, the enrolment under Settings → Account. The server only lists and removes them (`removeAllPasskeys`, `resetTwoFactor`, for an admin). Safari opens `navigator.credentials` only straight from a click, so keep the call first in its handler. A test cannot drive a passkey: the tests cover the server side and sign in with the password.
- Tests sign people in through `sessionFor` in `test/fixtures.ts` (a Better Auth password sign-in, answering the `cookie` header), `tokenOf` turns that into the bearer token for the API, and `mailbox()` makes a person with a `credential` account.
- The Workspace API (`/api/v1/*`, [docs/API.md](docs/API.md)) reads `Authorization: Bearer <session token>` (Better Auth's `bearer` plugin; `POST /api/auth/sign-in/email` answers the token in `set-auth-token`) through `getSessionUser`, which takes a session cookie too. A request without a usable token is `401` with `WWW-Authenticate: Bearer realm="Workspace API"`. There are no scopes. A route calls the server modules the console's loaders call and answers the same shapes; a new endpoint is a route in its section, a row in `docs/API.md` and a case in `test/api.test.ts`.

### Single sign-on and Duo

- The workspace is an OpenID Connect provider for other apps ([docs/SSO.md](docs/SSO.md)): `app/lib/sso/provider.server.ts` answers `SSO_PATHS` (`/.well-known/openid-configuration`, `/oauth/*`), served by `route` in `workers/worker.ts` before Better Auth, so the tests reach it through `exports.default.fetch`. Applications, their lists and roles are `clients.server.ts`; the Applications tab is `sso/settings.server.ts` (`applicationsSettings`, `applicationsIntent`). It reads the person through `getSessionIdentity` (`sid`, `auth_time`, `amr`), never a cookie of its own. `handleSsoRequest` takes `now`, so a test ages a code or a token by passing a time.
- A session says how it was signed in: `sessions.amr` (space-separated RFC 8176 methods), written by the `session.create.before` hook from the endpoint that made it (`amrForSignIn`: the password, the TOTP code, a passkey with or without its User Verified flag) or by its maker (`startSession`). A new way to sign in names its `amr` there, or its tokens say nothing about it.
- Duo is optional: on only while `DUO_CLIENT_ID`, `DUO_CLIENT_SECRET` and `DUO_API_HOST` are all set (`duoEnabled`). On, `passwordSignIn` checks the password itself (`checkPassword`), sends the browser to Duo's prompt with the challenge sealed in a cookie on `/auth/duo` (purpose `duo-challenge`), and `finishDuoSignIn` makes the Better Auth session through `startSession` (`internalAdapter.createSession` and the cookie signed as better-call signs it). Duo down: a person with an authenticator app goes on to `/two-factor` through Better Auth's sign-in, anyone else is refused unless the var `DUO_FAIL_OPEN` is `true`. Off, the sign-in is Better Auth's own, the authenticator app the second factor. A passkey signs in on its own either way. The tests drive Duo against `fakeDuo` (`test/fake-duo.ts`) and never call Duo.
- The signing key's private half is sealed (`sealSecret`, purpose `oauth-signing-key`); rotating `SESSION_SECRET` retires it on next use and makes a new one, so apps fetch the new key set.

### Mail

- Inbound mail only reaches the Worker through an Email Routing rule; `addresses` in `wrangler.jsonc` makes Wrangler create one per entry on deploy, a literal address or the `*@<MAIL_DOMAIN>` catch-all, and taking over a rule made in the dashboard is a destructive change Wrangler applies only after an interactive yes.
- Mail for an address that is no mailbox or alias is refused (`setReject`), so the sender gets a bounce; a `+tag` reaches the address before the plus; a message delivered to two of our addresses arrives once per mailbox, deduplicated on Message-ID.
- A group inbox is a `users` row of kind `group` (no password, passkey or session: the `session.create.before` hook refuses one) with a `groups` row for its mode and `group_members` for its people (`app/lib/groups.server.ts` makes and changes them, Settings → Groups). Where an address delivers is `resolveDelivery` (`app/lib/mail/groups.server.ts`): a distribution group files a copy in each active member's mailbox, a shared one into its own. A list of people (People, Drive's colleagues, Calendar's invitations, signing) names `users.kind = 'person'`. A shared inbox is opened as `/mail?box=<group>`: every Mail loader and server function resolves `box` through `mailboxFor` (`mailContext` in `mail/context.server.ts`) and then acts as that owner, so a component that calls a Mail server function passes the box on (`useMailbox`, `inMailbox`, the composer's hidden field) and a link inside Mail keeps it (`listParams`, `listSearch`). The Workspace API takes the same `?box=` on every `/mail` route (`inMailbox` in `app/lib/api/mail.server.ts`, through `mailboxFor`), and `GET /me` lists the person's shared inboxes (`mailboxes`); the Assistant, Mail's AI and the search by meaning stay on the person's own mailbox.
- Mail that arrives, an import's history and the copy of a sent message are all filed by `fileMessage` (`app/lib/mail/filing.server.ts`), whose policy (`arrival`, `history`, `sent`) says what the message does to an existing conversation; the filters, the spam filter and the vacation responder stay with `ingest.server.ts`.
- A message to one of the owner's own addresses comes back through Email Routing within a second, often before `sendMail` has filed the sent row: whichever side files second finds the other's row and makes the two one message (`sameMessage`); `test/send.test.ts` covers both orders.
- Every write to a conversation's state (folder, `trashed_at`, snooze, star, mute, read, labels, the counters) goes through `app/lib/mail/threads.server.ts`; `mailbox.server.ts` reads. A page of a list and an opened thread are `listPage` and `openThread` in `reads.server.ts`, the one place the console's loaders and `/api/v1` get them: a rule of either (which folder, the page, marking read, the HTML made safe, whose images load) goes there, never in a route. An action answers its undo as a record of what it changed, sealed with `sealSecret` (purpose `mail-undo`), and `undoThreadAction` puts that back without checking or learning again. The functions take `now`, so a test snoozes or trashes in the past instead of rewriting a row.
- Each view and each intent's effect is defined once in `app/lib/mail/views.ts`: a condition the list reads in JS (`matches`) and the server as SQL (`conditionSql`), and `intentEffect`, which `applyThreadAction` does and `leavesView` predicts. `test/views.test.ts` holds the two readings to the same answers.
- The cron (`triggers.crons`, every minute) is `workers/scheduled.ts`: `wakeSnoozed`, `sendDueDrafts`, `runImports`, `runRemovals` (another batch of each person an admin removed, `app/lib/removal.server.ts`), then `indexForSearch` (the search by meaning, at most about 80 of the invocation's queries), then the prunes (`pruneDrive`, `pruneExpired`, a batch of 10 each across every drive and mailbox, and `pruneSpamTokens`, the one mailbox whose turn the minute of the day is), each in its own `try` so a broken import never holds back the mail. The cron's D1 queries share one invocation's limit, so the prunes come last and their batches stay small; a prune goes on past an item that fails and throws once the batch is done (`eachOf`, `throwFailures` in `app/lib/batch.ts`), or a failing item would come first again every minute. `handleScheduled` takes the minute the run was scheduled for (`at`), which a test passes. Two runs can overlap, so a scheduled message is claimed (its `scheduled_at` moved on where nobody else moved it) and an import leased (`lease_until`) before either is worked on. `wakeSnoozed`, `pruneDrive` and `pruneExpired` name every owner (`user_id in (select id from users)`) so they search their indexes instead of scanning the table.
- The spam filter (`app/lib/mail/spam.ts`, `spam.server.ts`) trusts a header about authentication only from Cloudflare's MX: the block above the first `Received` line another server wrote, and in it the topmost `Authentication-Results` of `mx.cloudflare.net` and `X-CF-SpamH-Score`. A new rule reads `signals.checks`, never `headerOf`. A message without them (local dev, the tests) is scored on its content alone; an imported message is never scored.
- A domain whose DMARC policy is `p=none` lets Email Routing forward forgeries of the workspace's own domain; the `own-domain` rule is what puts them in Spam. The filter teaches itself only from what the rules alone score 8 or more and from people the owner writes to, never from its learnt words and never from a filter; a move the owner makes into Spam or out of it learns, a filed message's placement never does, and an undo takes back what its action taught (`restoreLearnt`).
- A mailbox import never runs the filters or the vacation responder, and no notification fires for it. Graph's messages are keyset-paged on `receivedDateTime` from `cursor_json`, 50 a page because the duplicate check binds one Message-ID each. The tests bring a `MailSource` of their own and never call Microsoft. The tokens are sealed with a key from `SESSION_SECRET` (`app/lib/secret-box.server.ts`, as a person's GitHub token is): rotating it fails every running import and reads every GitHub connection as none.
- The HTML part of a message is shown by `HtmlMessage` in an iframe with `sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox"` and a CSP in the document itself (`mailDocument`): no script, no form, images only from this origin's signed file links until the reader presses "Load images" (a sender on `image_senders` skips that, except in Spam). Never render a message's HTML outside that frame; the one exception is the rich editor, which passes everything it starts from (the quote, a draft, a signature) through DOMPurify first (`editorMarkup`). No CSP holds an image back there, so a quote's images from the web wait in `data-held-` attributes (`images: "hold"` in `quotableHtml`) unless `loadsImages` says opening the original loads them, and `sanitizeOutgoingHtml` puts them back (`images: "restore"`). Only `hold` writes a `data-held-` attribute: one in a sender's markup goes in every mode, or the send would bring to life what the owner never saw.
- `sanitizeHtml` reads markup its own way, not as a browser does, so its output must stay canonical: every tag written anew, every `<` in text and every `<` or `>` in an attribute escaped; `test/sanitize.test.ts` holds the line. It finds the markup in one forward pass (`nextMarkup` in `app/lib/mail/markup.ts`) and reads at most `MAX_HTML` characters, ending a part it cut with a "[Message clipped …]" line; the composer's body over that is refused on send (`composeBody`), never cut. An expression that searches markup for a close (`[\s\S]*?-->`, `[^>]*>`, `<style\b[^>]*>[\s\S]*?<\/style>`) searches again from every opening without one, which took time quadratic in the part's size (#3591): the style element comes out of sanitised markup through `withoutStyles`. The composer's markup goes through `sanitizeOutgoingHtml` on send, and a form that posts `text` without `html` takes the plain-text path.
- An HTML signature's images are `data:` URIs in its markup (a hosted image would need a public link); `dataImages` lets them through for `sanitizeSignatureHtml` only, never for mail that arrives or the composer's body, and `inlineDataImages` turns each into a `cid:` inline attachment on send.
- The rich editor's hidden input (`RichEditor`, the markup the form posts) takes no `value` or `defaultValue` prop: a hidden input's value is its `value` attribute, which React writes back on every re-render, so with `defaultValue` an autosave between keystrokes posted an empty draft. Only the editor's `sync` and its mount effect set it.
- A moment shown in the reader's time zone (`Timestamp`, `snoozeLabel`, the calendar grid, the grouped tasks) is rendered only once `useHydrated()` is true; the server formats in UTC, and `suppressHydrationWarning` would only hide the difference (React keeps the server's text). Never format a local time while the server renders.
- `/mail` is a layout route (`app/routes/_app/mail.tsx`): it loads the list and renders the thread or the composer beside it. Its search params (`folder`, `q`, `page`, `label`) are what a link to a thread keeps (`listParams`); a child's own params (`draft`, `reply`) stay out of the layout's `loaderDeps`, or every composer state would reload the list. The list's shortcuts act on its selection; the thread's act on the open conversation only while nothing is selected.
- The router keeps search params as strings (`parseSearchWith` in `app/router.tsx`), but TanStack's decoder still turns a value that looks like a number or a boolean into one first, so such a param is `z.coerce.string()` in its route's schema (`q`, `page`, `/login`'s `reset`).
- Every loader in the console runs again once a minute and when the tab comes back (`useRefresh` in `app/routes/_app/route.tsx`). Each goes through `keepShown` (`app/lib/keep-shown.ts`): a failed run for a view the page already shows answers with that view's data and reports the error; a route the page enters fails into the section's own `SectionError`, which each route sets as its own `errorComponent` (Mail's list, conversation and composer each theirs): on a first load the server renders the failing route's error component, never a layout's, which catches only in the browser. Their server functions are called with `serverFnFetch` (`app/lib/server-fn-fetch.ts`), which names the method and path of a call that got no readable answer. `test/console-loaders.test.ts` reads the route files and fails a loader under `/_app` that skips `keepShown`, `serverFnFetch` or an error state.
- An action on conversations hides the rows it takes out of the view the moment it starts (`useThreadActions`, `leavesView`), and they come back if it fails, or once `router.invalidate({ sync: true })` has the reloaded list; a bare `router.invalidate()` resolves at once with the old data.
- A link mailed for a one-time action (`/reset-password`, `/confirm-recovery`) carries its token in the URL fragment, read on the client with `useLinkToken` (`app/lib/link-token.ts`) and posted to a server function: Workers Logs keep every request's full URL. The token is stored as its SHA-256 and spent by deleting its row (`delete … returning`).
- Values a cookie or an address carries go through `app/lib/sealed.ts` (HMAC under `SESSION_SECRET`, per purpose); secrets at rest through `secret-box.server.ts` (AES-GCM); file links are signed (`signFileUrl`, six hours) and need no cookie, since the sandboxed frame sends none.
- Deleting is only final from the trash (`deleteThreadForever`), and it removes the raw `.eml` and the files from R2 with the rows. A filter can name a label that was deleted since: `filterOutcome` skips it.
- `useShortcuts` leaves Escape to an open `<dialog>`, and a `<dialog>` or anything with `role="dialog"` or `role="menu"` counts as typing, so single-key shortcuts stay quiet inside them.

### OpenPGP

- OpenPGP.js is loaded on first use (`loadOpenPgp` in `app/lib/mail/pgp/openpgp.server.ts`), never imported with the Worker, and every call that reads a message or a key passes `PGP_CONFIG`: its defaults decompress a message to any size and let a key's Argon2 ask for a gigabyte. Keys are made `ecc` on `curve25519Legacy` (version 4), which GnuPG 2.2 and every mail client read; OpenPGP.js's own default (RFC 9580 Ed25519) they do not.
- What arrives encrypted is decrypted once, on arrival, with the owner's key (`openPgpMail` in `ingest.server.ts`, before the filters and the spam filter), and kept opened: search, the Assistant and the API read it as any mail. This is not end-to-end, and the docs say so; don't add a path that stores ciphertext and decrypts on read. The `.eml` in R2 stays as it came, which "Check again" (`recheckPgpMessage`) opens anew.
- The private key is sealed (`sealSecret`, purpose `pgp-private-key`) unlocked, so the Worker signs without a passphrase; rotating `SESSION_SECRET` loses it (`ownPrivateKey` then throws a PgpError that says so). A refusal a person can act on is a `PgpError`; `send.server.ts` turns it into a SendError (`pgpOrRefuse`).
- A signature is checked against the sender's key alone (`keyFor` in `lookup.server.ts`: a colleague's `pgp_keys` row for an address of `MAIL_DOMAIN`, never anything else for it; else `pgp_peer_keys`; else WKD), never against a key the message carries, or anyone could sign as anyone. An Autocrypt header teaches a key only from mail that is not spam and passed DMARC or DKIM for the From's domain (`learnAutocrypt`, which reads `signals.checks` as the spam filter does).
- A PGP/MIME signature covers the first part's exact bytes, so `pgp/mime.ts` reads and writes MIME itself, text one character per byte (`byteString`), never through postal-mime or a `TextDecoder`. The signed part is written once (`writePart`) and that same `Part` goes into `multipart/signed`; its text is base64 so no relay re-encodes it. Like the sanitiser, it reads in one pass with `indexOf`, no regex that searches again from each start.
- Signed or encrypted mail goes out through `sendRawMail` (`@rivi-software/workers-mail` 0.2.0), not `sendMail`: SES's raw send with the `Autocrypt` header in `sesOnlyHeaders` (Email Service's allowlist refuses it), or the binding's legacy `EmailMessage`, one per recipient, each copy with its own `Message-ID`. Bcc is in the envelope (`recipients`), never in the message, and an encrypted message names a Bcc recipient's key by a wildcard key ID only (`encryptFor`), since the To and Cc recipients get the same ciphertext. Encryption with a recipient that has no key is refused, never sent in the clear.
- An inline block protects only itself: text around it, a file beside it, or an encrypted block nobody signed beside a signed one makes the status `partial` (`isPartial`) (amber in the thread), and of several blocks the worst verdict stands, never the last. Encrypted mail without the sender's good signature is amber too: anyone with the owner's public key can write it, or send a captured ciphertext on under their own name hoping for a quoting reply.
- The Worker serves WKD itself (`isWkdPath`, `serveWkd`, before Better Auth in `route`), answering only a request whose `?l=` names an active person's address that their key names; a deployment routes `openpgpkey.<MAIL_DOMAIN>/.well-known/openpgpkey/*` to it (README, OpenPGP). `lookupWkd` remembers a miss in KV for a day; the tests pass a `fetch` of their own through `ingestInboundEmail`'s `options` and never reach a real domain.

The customer's page is under `/s/sign/` (the code as form posts through `visitorPost`, signing and declining as JSON posts to the page's own route under the same origin rule, its PDF at `/s/sign/$token/document`), and `SECRET_PATHS` lists `/s/sign/$token` before `/s/$token`.
