# Workspace: agent instructions

Workspace is an open-source workspace on Cloudflare Workers: **Mail** (every person has a mailbox on `MAIL_DOMAIN`, receives through Email Routing and sends through `@rivi-software/workers-mail`: Amazon SES once the Worker holds its key, the Email Service `send_email` binding until then and when SES refuses a message), **Drive** (folders and files in the `DRIVE` bucket, shared inside the workspace or outside it by a link or an invite under `/s/`, and PDFs sent for signatures under `/drive/sign` and `/s/sign/`), the **Assistant** (a chat over the person's own mail and files on Workers AI through AI Gateway, or Anthropic, or a mock; tools that search mail, read a conversation, search Drive, read a text file and prepare a draft), **Calendar** and **Tasks** (events with invited colleagues; to-dos linked with GitHub Issues through a personal token kept sealed). One Worker: TanStack Start on the Cloudflare Vite plugin, D1 with Drizzle, R2 for raw messages and files, KV for throttles and small state, sign-in on Better Auth (`app/lib/auth.server.ts`), and the Workspace API for other clients at `/api/v1` (`app/lib/api/`, [docs/API.md](docs/API.md)). The README covers the product and the deploy; [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) the layout, the data model and the flows; [GLOSSARY.md](GLOSSARY.md) the words. Write plain English in names, comments and docs; a comment says why.

## Commands

- `pnpm run dev`: `wrangler types`, then Vite on http://localhost:5174 with every binding in Miniflare. Inbound mail is a POST to `/cdn-cgi/local/email` (`pnpm run email:simulate "Subject" "Body"`), sent mail is written under `.wrangler/tmp/email/` instead of leaving the machine, and the cron runs only when asked: `curl "http://localhost:5174/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"`.
- First `cp .dev.vars.example .dev.vars` and `pnpm run setup` (the local D1 migrations plus the seed); sign in with `admin@example.com` / `password`. `.dev.vars.example` sets `AI_PROVIDER=mock`, so the Assistant answers without `wrangler login`; `workers-ai` or `anthropic` run the real model through the AI binding, which is remote even in local dev.
- `pnpm run check`: `wrangler types`, then `tsc -b` over `app/`, `workers/` and `test/`. `pnpm run lint` is Oxlint on the Ultracite config (`oxlint.config.ts`), `pnpm run format:check` Oxfmt (`pnpm run format` fixes; Markdown and JSON are not formatted), `pnpm run contracts:check` requires `migrations/` to match `app/db/schema.ts` and every recorded migration to match its hash in `migrations/JOURNAL.json`. `pnpm run verify:static` is the four together.
- `pnpm run test`: Vitest inside workerd (`@cloudflare/vitest-plugin`) with the D1 migrations applied to a fresh database. `vitest.config.ts` pins the `vars` of `wrangler.jsonc` (so the tests see `example.com` whether `.dev.vars` exists or not), `AI_PROVIDER=mock`, an empty PostHog token and empty SES secrets; `recordingEmail()` in `test/fixtures.ts` stands in for the `EMAIL` binding.
- `pnpm run build` then `pnpm run build:check`: the production build, `wrangler deploy --dry-run` of it, and `workers-bundle-check` (`workers-bundle-check.config.ts`), which fails on a source map the assets would serve, a value shaped like a secret in the build, or a forbidden marker in the Worker. `pnpm run smoke` runs `scripts/smoke.mjs` against a running server (`BASE_URL`): sign-in, an inbound message, the inbox, the thread, a reply through the binding, Sent, search, a Drive upload with its listing, file route and search, a link outside the workspace, Better Auth's session and sign-out, the Assistant on the mock model, Calendar, Tasks, and the password reset pages. CI runs it against `wrangler dev --local` on the build.
- `pnpm run verify` is the full gate. `pnpm run deploy` and `pnpm run deploy:production` deploy (README, Deploy). CI is `.github/workflows/ci.yml`; deploys from `main` are `.github/workflows/deploy.yml`, behind the repository variable `DEPLOYMENTS_ENABLED`, with `scripts/deploy-checks.mjs` before (main only, no placeholder binding id) and after (`APP_URL` answers `/api/health`). `.github/workflows/semgrep.yml` comments a pull request's new Semgrep findings, and `.github/workflows/rivi-bot.yml` runs RIVI Bot (rivi-software/tools) as `.github/rivi-bot.yml` on `main` says.

## Gotchas

### Configuration and the build

- `wrangler.jsonc` is the production configuration; `.dev.vars` overrides its `vars` locally. Never put a secret in `wrangler.jsonc` or commit `.dev.vars`.
- `worker-configuration.d.ts` is git-ignored and written by `wrangler types` (the `dev`, `check` and `build` scripts run it). It declares the secrets only when `.dev.vars` exists, so `app/env.d.ts` declares them for CI's typecheck; a new secret goes in `.dev.vars.example` and there.
- `app/routeTree.gen.ts` is generated by `pnpm run dev`/`pnpm run build` and committed; Oxfmt and Oxlint ignore it.
- Start's import protection fails the build when a route component reads from a `*.server.ts` module: what the client renders lives in a plain module (`app/lib/mail/folders.ts`, `views.ts`, `reads.ts`, `drive/drive.ts`, `drive/signing.ts`, `assistant/assistant.ts`), and the server-only functions stay in `*.server.ts`, called from loaders and server functions. The components call server functions from the `actions.ts` modules (`app/lib/mail/actions.ts` and its siblings), which import the `*.server.ts` modules for their handlers only.
- A `*.server.ts` module the tests import must not import `app/lib/request.server.ts`: its `@tanstack/react-start/server` import only loads inside the Vite build, which is why `auth.server.ts` carries its own `isSecure`.
- The Worker is one module, `createWorker` in `workers/worker.ts`: `fetch` (earlier builds' assets, Better Auth, the API, then Start; the security headers on every answer, errors reported to PostHog), `email` and `scheduled`. `workers/app.ts` passes Start's handler and `test/worker-entry.ts` (the tests' `SELF`) a stand-in that answers 404, since Start needs the Vite build. A new path the Worker serves itself goes into `route` there, and so into both; a test that needs Start to answer mounts `createWorker` with a Start of its own (`test/worker.test.ts`).
- pnpm 12 blocks a dependency's build script unless `pnpm-workspace.yaml` lists it under `allowBuilds`; a new dependency that compiles something (a native binary, a WASM blob) goes there, else it installs without building. `overrides` there pins transitive versions with advisories; remove one once its parent ships a fix.
- Nothing in the repository names a Cloudflare account: `wrangler.jsonc` carries placeholder ids until a deployment pastes its own (README, Deploy), and the tests and the smoke run against Miniflare alone.
- `scripts/create-admin.mjs` (`pnpm run admin:create --local|--remote --email … --name …`) makes or resets an admin straight in D1 through `wrangler d1 execute`: a new password hash, every session and the authenticator app gone, the account active and admin. It is the way back in for a locked-out admin, and the way the first admin is made in production.
- `workers-bundle-check.config.ts` forbids markers, never modules: Rolldown writes no source map for the chunks of virtual modules (Start's manifest and server function resolver, its own runtime), and a module rule fails every file it cannot see into. A marker must also be in a file of the project outside `node_modules`, or the check calls it stale.
- The build writes `dist/server/wrangler.json` and points Wrangler at it through `.wrangler/deploy`, so `wrangler deploy` and `wrangler dev` after a build serve the build; `.dev.vars` is read beside that config (CI copies it to `dist/server/`).

### Database and migrations

- A schema change goes through Drizzle: edit `app/db/schema.ts`, run `pnpm run db:generate`, commit the new file under `migrations/` with its `meta/` snapshot. `contracts:check` fails on a schema that differs from the migrations, and drizzle-kit cannot ask about a rename in CI. `db:generate` also records the new file's SHA-256 in `migrations/JOURNAL.json` (`@rivi-software/d1-migrations`), and `contracts:check` fails once a recorded migration is edited or deleted: a migration that ran never changes, the next one does the work.
- drizzle-kit writes an added column's `REFERENCES` without its `ON DELETE` action (the snapshot keeps it), so read the SQL and add the action by hand.
- The deploy applies the migrations before the Worker (about 15 seconds apart), and Drizzle names every column of `schema.ts` in its selects, so dropping a column breaks the running Worker until the deploy lands. A drop that must not interrupt takes two releases: the schema without the column first, the drop after.
- Better Auth's tables (`users`, `sessions`, `accounts`, `verifications`, `passkeys`, `two_factors`) are in the same schema and migrate the same way. Its dates are integer milliseconds (`instant` in the schema); the app's own columns are ISO text.
- D1 binds 100 values a query, and the tests' Miniflare refuses the 101st too. A list of ids that can reach 100 (a page, a selection, "Mark all as read", a message's References) goes in as one JSON array through `json_each` (`inIds` in `mailbox.server.ts`, `trainTokens` in `spam.server.ts`) or in slices (Drive's `chunks` of 90, the shared roots 20 a query), never as `inArray` or a multi-row `values`.

### Sign-in (Better Auth)

- Better Auth is one instance per `Env` (`authFor` in `app/lib/auth.server.ts`, a `WeakMap`), so the tests' stand-in envs each get their own; `authFor` answers a promise, since Better Auth and its plugins are imported on first use (`loadBetterAuth`), not with the Worker: the module graph is large, and only a request that signs someone in or reads a session needs it. Its error class comes from the small `@better-auth/core/error`, never from `better-auth/api`, which pulls the whole graph in. `createAuth` reads `APP_URL` for `baseURL`, `trustedOrigins` and the passkeys' `rpID`: passkeys and the sign-in forms work at that origin alone.
- The Worker serves `/api/auth/*` before TanStack Start (`isAuthPath` in `workers/worker.ts`), as it serves `/api/v1/*`, so the tests reach both through `SELF.fetch` without the Vite build.
- Sign-up, Better Auth's own password reset, email verification, change-email and delete-user are `disabledPaths`: admins make the accounts (`createPerson` in `users.server.ts`), and a forgotten password goes through `recovery.server.ts`. Better Auth's ids get the app's prefixes (`ID_PREFIXES`: `usr`, `ses`, `acc`, `ver`, `pk`, `tfa`).
- The password form is `passwordSignIn` in `app/lib/sign-in.server.ts`, one call from `/login`'s POST handler, in this order: `sameOriginPost` (Start's CSRF middleware in `app/start.ts` checks server functions only, not a route's own handlers; a form on another site would otherwise sign the browser in to the account it names), the form's own throttle (KV, 10 failures per client and address in 15 minutes: `loginThrottled`, `recordLoginFailure`, `clearLoginFailures`), a deactivated person told so, then `auth.api.signInEmail`. A post with neither `Sec-Fetch-Site` nor `Origin` passes, since no browser sent it; the smoke relies on that.
- Better Auth's own rate limits (`kvRateLimit`, a fixed window in KV, `customRules` per path) are a brake, not a lock: two requests in the same instant can both pass. The form's throttle is the one that counts failures.
- `/two-factor` (`secondFactorSignIn`) checks the origin the same way and posts the code, or a backup code, to Better Auth with the two-factor cookie the sign-in set; `trustDevice` is the 30-day checkbox. `next` always goes through `safeNext`: a path on this host, never another site.
- Sessions are rows in D1 (`sessions`), read on every request (`cookieCache` off), so ending one is immediate. `revokeSessions` deletes a person's rows; `setPassword` (an admin's one-time password, a reset link) writes the hash and revokes; `changeOwnPassword` goes through Better Auth's `changePassword` with `revokeOtherSessions` and answers the new session's cookie, so Settings keeps the browser signed in; `setPersonActive(false)` revokes, and the `session.create.before` hook refuses a deactivated person on every way in.
- The password hash is the `credential` row of `accounts`, PBKDF2 as `hashPassword` writes it. `scripts/create-admin.mjs` and `scripts/build-seed.mjs` write the same format, so a hash they wrote signs in through Better Auth; keep the three in step.
- Passkeys and the authenticator app go through the browser client (`app/lib/auth-client.ts`, a plain module the pages import): `authClient.signIn.passkey()` on the login page, the enrolment under Settings → Account. The server only lists and removes them (`removeAllPasskeys`, `resetTwoFactor`, for an admin). Safari opens `navigator.credentials` only straight from a click, so keep the call first in its handler. A test cannot drive a passkey: the tests cover the server side and sign in with the password.
- Tests sign people in through `sessionFor` in `test/fixtures.ts` (a Better Auth password sign-in, answering the `cookie` header), `tokenOf` turns that into the bearer token for the API, and `mailbox()` makes a person with a `credential` account.
- The Workspace API (`/api/v1/*`, [docs/API.md](docs/API.md)) reads `Authorization: Bearer <session token>` (Better Auth's `bearer` plugin; `POST /api/auth/sign-in/email` answers the token in `set-auth-token`) through `getSessionUser`, which takes a session cookie too. A request without a usable token is `401` with `WWW-Authenticate: Bearer realm="Workspace API"`. There are no scopes. A route calls the server modules the console's loaders call and answers the same shapes; a new endpoint is a route in its section, a row in `docs/API.md` and a case in `test/api.test.ts`.

### Mail

- Inbound mail only reaches the Worker through an Email Routing rule; `addresses` in `wrangler.jsonc` makes Wrangler create one per entry on deploy, a literal address or the `*@<MAIL_DOMAIN>` catch-all, and taking over a rule made in the dashboard is a destructive change Wrangler applies only after an interactive yes.
- Mail for an address that is no mailbox or alias is refused (`setReject`), so the sender gets a bounce; a `+tag` reaches the address before the plus; a message delivered to two of our addresses arrives once per mailbox, deduplicated on Message-ID.
- Mail that arrives, an import's history and the copy of a sent message are all filed by `fileMessage` (`app/lib/mail/filing.server.ts`), whose policy (`arrival`, `history`, `sent`) says what the message does to an existing conversation; the filters, the spam filter and the vacation responder stay with `ingest.server.ts`.
- A message to one of the owner's own addresses comes back through Email Routing within a second, often before `sendMail` has filed the sent row: whichever side files second finds the other's row and makes the two one message (`sameMessage`); `test/send.test.ts` covers both orders.
- Every write to a conversation's state (folder, `trashed_at`, snooze, star, mute, read, labels, the counters) goes through `app/lib/mail/threads.server.ts`; `mailbox.server.ts` reads. A page of a list and an opened thread are `listPage` and `openThread` in `reads.server.ts`, the one place the console's loaders and `/api/v1` get them: a rule of either (which folder, the page, marking read, the HTML made safe, whose images load) goes there, never in a route. An action answers its undo as a record of what it changed, sealed with `sealSecret` (purpose `mail-undo`), and `undoThreadAction` puts that back without checking or learning again. The functions take `now`, so a test snoozes or trashes in the past instead of rewriting a row.
- Each view and each intent's effect is defined once in `app/lib/mail/views.ts`: a condition the list reads in JS (`matches`) and the server as SQL (`conditionSql`), and `intentEffect`, which `applyThreadAction` does and `leavesView` predicts. `test/views.test.ts` holds the two readings to the same answers.
- The cron (`triggers.crons`, every minute) is `workers/scheduled.ts`: `wakeSnoozed`, `sendDueDrafts`, then `runImports`, each in its own `try` so a broken import never holds back the mail. Two runs can overlap, so a scheduled message is claimed (its `scheduled_at` moved on where nobody else moved it) and an import leased (`lease_until`) before either is worked on. `wakeSnoozed` names every mailbox (`user_id in (select id from users)`) so it searches `threads_user_snoozed_idx`.
- The spam filter (`app/lib/mail/spam.ts`, `spam.server.ts`) trusts a header about authentication only from Cloudflare's MX: the block above the first `Received` line another server wrote, and in it the topmost `Authentication-Results` of `mx.cloudflare.net` and `X-CF-SpamH-Score`. A new rule reads `signals.checks`, never `headerOf`. A message without them (local dev, the tests) is scored on its content alone; an imported message is never scored.
- A domain whose DMARC policy is `p=none` lets Email Routing forward forgeries of the workspace's own domain; the `own-domain` rule is what puts them in Spam. The filter teaches itself only from what the rules alone score 8 or more and from people the owner writes to, never from its learnt words and never from a filter; a move the owner makes into Spam or out of it learns, a filed message's placement never does, and an undo takes back what its action taught (`restoreLearnt`).
- A mailbox import never runs the filters or the vacation responder, and no notification fires for it. Graph's messages are keyset-paged on `receivedDateTime` from `cursor_json`, 50 a page because the duplicate check binds one Message-ID each. The tests bring a `MailSource` of their own and never call Microsoft. The tokens are sealed with a key from `SESSION_SECRET` (`app/lib/secret-box.server.ts`, as a person's GitHub token is): rotating it fails every running import and reads every GitHub connection as none.
- The HTML part of a message is shown by `HtmlMessage` in an iframe with `sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox"` and a CSP in the document itself (`mailDocument`): no script, no form, images only from this origin's signed file links until the reader presses "Load images" (a sender on `image_senders` skips that, except in Spam). Never render a message's HTML outside that frame; the one exception is the rich editor, which passes everything it starts from (the quote, a draft, a signature) through DOMPurify first (`editorMarkup`).
- `sanitizeHtml` reads markup with regular expressions, so its output must stay canonical: every tag written anew, every `<` in text and every `<` or `>` in an attribute escaped; `test/sanitize.test.ts` holds the line. The composer's markup goes through `sanitizeOutgoingHtml` on send, and a form that posts `text` without `html` takes the plain-text path.
- An HTML signature's images are `data:` URIs in its markup (a hosted image would need a public link); `dataImages` lets them through for `sanitizeSignatureHtml` only, never for mail that arrives or the composer's body, and `inlineDataImages` turns each into a `cid:` inline attachment on send.
- The rich editor's hidden input (`RichEditor`, the markup the form posts) takes no `value` or `defaultValue` prop: a hidden input's value is its `value` attribute, which React writes back on every re-render, so with `defaultValue` an autosave between keystrokes posted an empty draft. Only the editor's `sync` and its mount effect set it.
- A moment shown in the reader's time zone (`Timestamp`, `snoozeLabel`, the calendar grid, the grouped tasks) is rendered only once `useHydrated()` is true; the server formats in UTC, and `suppressHydrationWarning` would only hide the difference (React keeps the server's text). Never format a local time while the server renders.
- `/mail` is a layout route (`app/routes/_app/mail.tsx`): it loads the list and renders the thread or the composer beside it. Its search params (`folder`, `q`, `page`, `label`) are what a link to a thread keeps (`listParams`); a child's own params (`draft`, `reply`) stay out of the layout's `loaderDeps`, or every composer state would reload the list. The list's shortcuts act on its selection; the thread's act on the open conversation only while nothing is selected.
- The router keeps search params as strings (`parseSearchWith` in `app/router.tsx`), but TanStack's decoder still turns a value that looks like a number or a boolean into one first, so such a param is `z.coerce.string()` in its route's schema (`q`, `page`, `/login`'s `reset`).
- Every loader in the console runs again once a minute and when the tab comes back (`useRefresh` in `app/routes/_app/route.tsx`). Each goes through `keepShown` (`app/lib/keep-shown.ts`): a failed run for a view the page already shows answers with that view's data and reports the error; a route the page enters fails into the section's own `SectionError`. Their server functions are called with `serverFnFetch` (`app/lib/server-fn-fetch.ts`), which names the method and path of a call that got no readable answer. `test/console-loaders.test.ts` reads the route files and fails a loader under `/_app` that skips `keepShown`, `serverFnFetch` or an error state.
- An action on conversations hides the rows it takes out of the view the moment it starts (`useThreadActions`, `leavesView`), and they come back if it fails, or once `router.invalidate({ sync: true })` has the reloaded list; a bare `router.invalidate()` resolves at once with the old data.
- A link mailed for a one-time action (`/reset-password`, `/confirm-recovery`) carries its token in the URL fragment, read on the client with `useLinkToken` (`app/lib/link-token.ts`) and posted to a server function: Workers Logs keep every request's full URL. The token is stored as its SHA-256 and spent by deleting its row (`delete … returning`).
- Values a cookie or an address carries go through `app/lib/sealed.ts` (HMAC under `SESSION_SECRET`, per purpose); secrets at rest through `secret-box.server.ts` (AES-GCM); file links are signed (`signFileUrl`, six hours) and need no cookie, since the sandboxed frame sends none.
- Deleting is only final from the trash (`deleteThreadForever`), and it removes the raw `.eml` and the files from R2 with the rows. A filter can name a label that was deleted since: `filterOutcome` skips it.
- `useShortcuts` leaves Escape to an open `<dialog>`, and a `<dialog>` or anything with `role="dialog"` or `role="menu"` counts as typing, so single-key shortcuts stay quiet inside them.

### Drive and signing

- Drive's one gate is `app/lib/drive/access.server.ts`: listings, views, search, the move picker, breadcrumbs, every action, the file route and the Assistant keep what `reachAll`, `reach` or `reachFile` answers, and a link outside the workspace what `openLink` and `reachAllByLink`/`reachFileByLink` answer. Each caller names its `TrashPolicy` (`outside`, `own-trash`, `trash-view`). No other module reads `drive_shares` for access.
- A node's ancestors are the ids in its `path`, a subtree is `path GLOB prefix*` (not `LIKE`: ids carry `_`), and `moveNodes` rewrites a subtree's paths in one `UPDATE`; never set `parent_id` without `path`. Trashing marks only the node itself; what is under a trashed folder comes back with it.
- An upload's row exists before its bytes (`status` uploading, `upload_id` for a multipart one); only its uploader reaches it until it is whole (`runningUpload`), and `pruneDrive` abandons one a day old. A file up to 32 MiB is one PUT whose body streams into the bucket; a larger one goes in 16 MiB parts (R2 wants every part but the last the same size and at least 5 MiB). Uploads go by XMLHttpRequest, since `fetch` reports no upload progress.
- Files are served through `fileResponse` (`serve.server.ts`) by the session route (`/api/drive/files/$id`) and a link's (`/s/$token/file/$nodeId`) alike, so a change to the headers holds for both. A PDF gets `frame-ancestors 'self'` so the file page can frame it; `withSecurityHeaders` in `workers/worker.ts` keeps a response's own frame headers and only adds `frame-ancestors 'none'` where none is set.
- A link outside the workspace (`app/lib/drive/links.server.ts`) is viewer only and passes the gate on every request (`openLink`: not revoked or expired, sharing outside on, its creator active and still reaching the node). Everything a visitor asks for is under `/s/`: the page links with plain anchors and posts its forms to itself, so no server function is called from it, and its pass cookie is `Path=/s/`. An invite's code takes its try in one conditional `UPDATE` (`code_attempts < 5`) before it is compared. The tests call `sharedPage`, `sharedPagePost` and `sharedFileResponse` with a `Request` of their own, each from its own `cf-connecting-ip`, since the KV throttles count per client.
- Signing keeps its own copy of the PDF (`signing/<id>/original.pdf`) and reads the file through Drive's gate only when the request is sent; after that a request is its asker's and signer's alone (`ownRequest`). The customer's page is under `/s/sign/` (the code as form posts, signing and declining as JSON posts to the page's own route, its PDF at `/s/sign/$token/document`), and `SECRET_PATHS` lists `/s/sign/$token` before `/s/$token`.
- A step that changes a request's state is one conditional `UPDATE` on its status (`customerSigns` from `sent`, `finish` from `customer-signed`), so of two posts one wins; `finish` takes its claim back when the signed copy cannot be made or kept, and files the copy in Drive only after the request completed.
- A field's box is in fractions of its page as pdf.js shows it; `boxOn` in `signing-pdf.server.ts` maps it back onto the unrotated page, which `test/signing.test.ts` runs on all four rotations. pdf.js runs in the browser only (`loadPdfJs` behind `import.meta.env.SSR`); pdf-lib refuses a protected PDF, and a fillable original's form is flattened before the fields are drawn (`flattenForm`), so nobody can type over a signed copy.

### Assistant

- The Assistant answers through `/api/assistant/chat`, one call into `answerChat` (`app/lib/assistant/chat.server.ts`): the answer is stored in `onFinish`, which the SDK awaits before the stream closes, and the route's `waitUntil(done)` keeps the Worker for it. The tests read `response.text()` to the end, then await `done`.
- Every tool in `tools.server.ts` goes through the same gates as the pages, answers an `{ error }` rather than throwing, and writes nothing but a draft (`create_draft`). The tools never read Mail's tables, its bucket or its route paths: `app/lib/mail/mail.server.ts` is Mail's interface for them, and `app/lib/mail/links.ts` and `nodeHref` in `drive/drive.ts` are the links.
- `AI_PROVIDER=mock` (the tests, `.dev.vars.example`) is a `MockLanguageModelV4` in `provider.server.ts` that calls a tool on a few phrasings ("search my mail for …", "find files named …", "read the conversation th_…", "draft a reply to th_… saying …") and echoes anything else. The vars are typed from `wrangler.jsonc` as literals, so the module reads `AI_PROVIDER` and `AI_CHAT_MODEL` through a `string` cast.
- The page's chat is the AI SDK's `AbstractChat` with a React state of its own (`app/components/assistant/use-chat.ts`), not `@ai-sdk/react`; the transport posts only the person's newest message, and the server holds the history. A message's parts are stored and loaded as `StoredMessage` (`assistant.ts`), JSON through and through.
- The assistant's Markdown is rendered as React nodes (`markdown.tsx`), never through `innerHTML`; a link opens only on http(s), mailto or a path on this site (`safeHref`), and a path goes through the router.

### Calendar and Tasks

- An event is stored as instants with the zone it was made in (`calendar_events.time_zone`), and `occurrences` in `app/lib/calendar/calendar.ts` steps a repeat in that zone, so a weekly 10:00 stays 10:00 across the DST change; an all-day event is its days' UTC midnights, read as dates and never through the reader's zone. A task is due on a day (`tasks.due_on`), never a moment. `test/calendar.test.ts` runs the zone math on Europe/Amsterdam.
- GitHub for Tasks is each person's own token, never a secret of the Worker, and every function in `app/lib/tasks/github.server.ts` takes a `fetch`: a test lays an in-memory GitHub over it (`fakeGitHub` in `test/tasks.test.ts`) and nothing reaches api.github.com. What a page reads from GitHub goes through `callLink` (`app/lib/link.ts`) and never fails the page. Marking a linked task done closes the issue first and keeps the task open when GitHub refuses (`setTaskDone`).

### PostHog (optional)

- PostHog is off without `POSTHOG_PROJECT_TOKEN` (`.dev.vars.example` and `vitest.config.ts` leave it empty). In the browser it is error tracking only: `posthogOptions` in `app/lib/posthog-config.ts` turns off everything that records a page or a click, `stripQueries` takes the query and fragment off every address, `advanced_disable_flags` keeps the flags request from leaving, and `SECRET_PATHS` redacts a link's token. A new property that can hold a URL with a query goes through `withoutQuery`.
- The Worker reports the Assistant's calls to AI observability (`app/lib/ai-telemetry/`, registered in `app/lib/assistant/telemetry.server.ts`): a turn is a trace on the person, and its text leaves only where `AI_TEXT_ANALYTICS` is `on`, credentials masked and every string bounded. `test/assistant-telemetry.test.ts` holds both states; a test that reads what would be reported uses `installPostHogForTests` from `@rivi-software/posthog-tanstack-start`.

### The console

- `HtmlMessage` sizes its frame from the message's document as soon as it is parsed, never from the frame's `load`: `load` waits for every image, and a tracking pixel that never answers held a newsletter at the frame's first 120 px. Setting `srcDoc` replaces the frame's document a task or more later, so a layout effect notes the document there in that commit and measures only the one that replaces it.
- The theme lives in `localStorage`, so the server cannot know how a message reads: `mailReading` runs on the client and `HtmlMessage` leaves the frame empty until it has. A dark reading adapts the message's colours (`app/lib/mail/colors.ts`, in OKLab) and lets the message's own `prefers-color-scheme: dark` rules go over them; `mailDocument` drops every declaration in viewport-height units (inside the frame `100vh` is the frame's own height) and rewrites the message's `prefers-color-scheme` queries to the reading. Its CSS rewriting relies on the sanitiser's output, every attribute value double-quoted: never point it at raw HTML.
- The sidebar (`app/routes/_app/route.tsx`) switches module by pathname, and `UploadProvider` sits above the shell with `ToastProvider`, so the sidebar's New menu, a dropped file and the file pages share one upload queue and the panel bottom right. The Drive listing reuses `MailSelectionProvider` for its selection and `useListNavigation` for `j`/`k` on `[data-row]`.
- On a phone the console is a web app (`public/manifest.webmanifest`, the metas and icons in `routes/__root.tsx`): the page runs under the status bar and the home indicator (`viewport-fit=cover`), so the shell keeps clear of them with the `pt-safe`, `pb-safe`, `pb-dock` and `bottom-dock` utilities in `app.css`, and what floats at the bottom (toasts, the uploads panel, the new version notice) uses `bottom-dock`, which also clears the tab bar a phone screen has (`TabBar`, below `sm`).
- A deploy replaces the build a tab runs: `@rivi-software/deploy-watch` writes the build's id into every page and `dist/client/build.json`, `NewVersionNotice` offers the reload, `SectionError` reloads on a chunk a deploy removed, and the Worker serves an earlier build's chunk from `PREVIOUS_ASSETS` for seven days (`pnpm run deploy:assets`). The smoke finds the composer's form by its `/_serverFn/` action (the list's search form comes first) and matches a button's attributes in any order.

### Tests

- `vitest.config.ts` sets `fsModuleCache: false`: with Vitest's on-disk module cache, the Cloudflare pool hands a runner every cached module of a file's graph in one WebSocket message, and workerd closes a socket on a message over 1 MiB (close code 1009), so with Better Auth's graph warm a runner died at random on its way up ("Worker exited unexpectedly during started state"). Off, the modules come one by one; keep it off until the pool splits that message.
- One file per area under `test/`: `ingest`, `filing`, `send`, `mailbox`, `organise`, `threads`, `views`, `spam`, `schedule`, `import`, `signatures`, `sanitize`, `images`, `recovery`, `sessions`, `people`, `drive`, `drive-links`, `signing`, `assistant`, `assistant-telemetry`, `calendar`, `tasks`, `api`, `worker`, `posthog`, `console-loaders`, `keep-shown`. `test/setup.ts` applies the migrations (`TEST_MIGRATIONS`, read by `vitest.config.ts`); `test/stub-env.ts` lays a stub over the Worker's `Env` for a module that only needs a few bindings; `test/signing-fixtures.ts` makes PDFs.
- A test ages a session, a code or a link by passing a time (`now`, `at`), never by rewriting a row. A test that sends mail reads it back from `recordingEmail()`; one that sends through SES lays the three SES values over its env and spies on `fetch` (`test/send.test.ts`).
